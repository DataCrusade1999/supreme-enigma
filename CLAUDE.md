# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

Per-area detail lives in `.claude/rules/` (`web.md`, `lambda.md`, `infra.md`), path-scoped so each loads only when you touch that project. Anything needed *before* opening a file — commands, branch/PR process, cross-cutting gotchas — stays here.

## Structure

Three independent sibling projects, no monorepo tooling (no workspaces/Turborepo/Nx):
- `web/` — Next.js 16 + React 19 + TypeScript frontend, deployed to Vercel (`root_directory = "web"`; Vercel builds a push only when its last commit touches `web/` or `content/`, see Gotchas). Public portfolio pages live in the `web/app/(site)/` route group and have no auth check. The gated areas are the whole `/tools` namespace, the `/api/looper/*`, `/api/resume/*`, `/api/newsletter/*` and `/api/news-desk/*` routes, and the Keystatic admin (`/keystatic`, `/api/keystatic/*`). `web/lib/route-gate.ts` is the single source of truth for what's gated, for the list of tools, and, through `ROUTE_ACTIONS`, for which Cedar action each gated route needs. Amazon Verified Permissions decides every gated request (`web/lib/authz/`, policies in `infra/shared/cedar/`).
- `lambda/` — Python 3.12 DSP pipeline (audio loop processing), packaged as a Lambda container image.
- `infra/bootstrap/` — Terraform, applied once manually, creates only the Terraform state S3 bucket. Never destroyed by the kill switch.
- `infra/shared/` — Terraform, remote state, the one-of-each resources: the shared ECR repo, IAM roles (no IAM users — GitHub Actions and Vercel authenticate via OIDC), the Vercel project, Cognito, SES, DNS and budget alerts. Applied by CI from `dev` only (#345): a `shared` change reaches production when it merges to `dev`.
- `infra/modules/environment/` and `infra/envs/{dev,stage,main}/` — one Terraform stack and one state per environment, each calling the module once: that branch's S3 bucket, Lambda function, invocation alarm and the two Vercel env vars that point at them (see Branching & releases). Split from the single `infra/main` state in #327.
- `content/` — repo root, sibling to `web/`: git-backed blog content managed by Keystatic (GitHub mode), separate from the hand-written `web/content/projects.ts`/`resume.ts` data files — see `docs/superpowers/specs/2026-08-01-portfolio-blog-design.md` for why.
- `docs/superpowers/specs/` and `docs/superpowers/plans/` — the design specs and TDD implementation plans this project was built from (one pair per phase: the original bgm-looper build, the portfolio-site restructuring, the blog, etc.); check here for the "why" behind existing decisions before assuming something is undocumented.
- `ARCHITECTURE.md` (repo root) — architecture + measured cost breakdown.
- Keep scratch worktrees out of the tree (`.gitignore` covers `.claude/worktrees/` and `.worktrees/`) so `grep`/`find` from the repo root never hits duplicate checkouts.

## Commands

- App unit tests: `cd web && npm test` (= `vitest run`). **This is a fraction of the CI gate** — CI runs Trivy, lint, Vitest, pytest and Linux Playwright one after another in a single `test` job, and `deploy`/`release` need it green. Windows and macOS Playwright run in `e2e-cross-os`, on PRs into `main` only (macOS bills ~10x Linux minutes, Windows ~2x). `chromatic` (visual regression; PRs into `dev`, and `dev` pushes that touch `web/` or `deploy.yml`) is deliberately absent from every `needs:` — it reports but never blocks. The free plan's 2,000 Actions minutes/month are the constraint behind the CI layout — see "CI minutes" under Branching & releases before adding a job or a trigger.
- App e2e tests: `cd web && npm run test:e2e` (= `playwright test`, specs in `web/e2e/`). Needs a one-time `npx playwright install chromium`. It builds and serves the app itself — see `.claude/rules/web.md`.
- App lint: `cd web && npm run lint` (ESLint via `eslint-config-next`, config in `eslint.config.mjs`).
- App dev: `cd web && COOKIE_SECRET=devsecret COGNITO_DOMAIN=https://auth.ashutosh-pandey.com COGNITO_CLIENT_ID=… COGNITO_USER_POOL_ID=… AUTHZ_MODE=local npm run dev`. Local sign-in needs the real `COGNITO_*` values (the Vercel env vars Terraform sets; `http://localhost:3000/api/auth/callback` is a registered callback). Without them the public pages still run; only sign-in fails. `AUTHZ_MODE=local` decides gated requests from `infra/shared/cedar/` in-process, from the groups in your ID token; without it the proxy needs `AVP_POLICY_STORE_ID` and AWS credentials, and fails closed.
- App build: `cd web && KEYSTATIC_GITHUB_CLIENT_ID=dummy KEYSTATIC_GITHUB_CLIENT_SECRET=dummy KEYSTATIC_SECRET=dummy npm run build` — Keystatic's `github` mode needs all three or the build dies after compiling with `Failed to collect configuration for /api/keystatic/[...params]` (detail in `.claude/rules/web.md`); dummy values are fine for a local build, the real ones are only needed to actually authenticate against GitHub.
- Lambda tests: `cd lambda && .venv/Scripts/python -m pytest -q` on Windows (`.venv/bin/python -m pytest -q` on macOS/Linux). `pytest.ini` sets `pythonpath = src`. Deps live in `lambda/.venv` (local Python 3.13, CI 3.12), deliberately not the global interpreter — setup and the version rationale are in `.claude/rules/lambda.md`; re-run its `pip install` after any Dependabot bump.
- Terraform: `aws sso login --profile personal` (the profile is IAM Identity Center, not an access key; sessions last 12 hours), `export AWS_PROFILE=personal` (no backend block names a profile), then run from the stack's directory (`infra/shared` or `infra/envs/<env>`) with `-var-file=terraform.tfvars`. That file is gitignored (`*.tfvars`), one per stack. `infra/shared`'s has **seven required variables, none with a default** — `vercel_api_token`, `app_password`, `github_repo`, `alert_email`, `openrouter_api_key`, `google_client_id`, `google_client_secret` — so a fresh clone fails with `No value for required variable` until all seven are set; each env stack's needs only `vercel_api_token`. Each directory's `terraform.tfvars.example` is the committed template; copy it across and fill it in. Bootstrap order, `ignore_changes`, and the profile gotcha are in `.claude/rules/infra.md`. CI plans every infra PR and applies on push (`.github/workflows/terraform.yml`); local runs are the break-glass path.

## Branching & releases

- Three permanent branches: `dev` → `stage` → `main`. `dev` is the GitHub default branch — new local branches and PRs target `dev` by default. Promote by opening a PR `dev → stage`, then `stage → main` once QA'd.
- Live URLs (see README's Environments table too): `main` → https://ashutosh-pandey.com, `stage` → https://stage.ashutosh-pandey.com, `dev` → https://dev.ashutosh-pandey.com (`www.` redirects to the apex). The `vercel.app` URLs still serve too: `main` → https://bgm-looper.vercel.app, `stage` → https://bgm-looper-git-stage-ashutosh-pandeys-projects-77cb3a00.vercel.app, `dev` → https://bgm-looper-git-dev-ashutosh-pandeys-projects-77cb3a00.vercel.app.
- Terraform is four stacks with four states, split by shared-vs-per-branch: `infra/shared` holds the one-of-each resources used by all three branches (ECR repo, the GitHub and Vercel OIDC providers with the `ci_deploy` role and the production and preview Vercel roles, the Vercel project, budget alerts, env-agnostic secrets); `infra/envs/<env>` holds that branch's resources through `infra/modules/environment` (its S3 bucket, Lambda function and exec role, alarm, its Vercel IAM policy, and the Vercel env var overrides that point at them). Neither reads the other's state: `shared` builds the env bucket and function ARNs for its IAM policies from fixed names, and the env stacks look up the Vercel roles, ECR repo, SNS topic and Vercel project with `data` sources. On a fresh build apply `shared` first.
- Each branch has its own full backend: separate Lambda functions (`bgm-looper-processor`, `-dev`, `-stage`), separate S3 buckets (`portfolio-data-<account>`, `-dev-<account>`, `-stage-<account>`; renamed from `bgm-looper-audio-*` in #273 because they hold resume and News Desk data too), one shared ECR repo with per-branch tag prefixes (`main-<sha>`, `dev-<sha>`, `stage-<sha>`; no `:latest` — dropped 2026-08-06 since it was unused by the actual deploy step and could be silently overwritten). Each env stack has one `module.environment.aws_s3_bucket.data` and one `module.environment.aws_lambda_function.this`; `main`'s names carry no suffix. Each has its own exec role, `bgm-looper-lambda-exec-<env>`, scoped to its own bucket.
- Vercel points each branch at its own bucket and function through `git_branch`-scoped `S3_BUCKET_NAME`/`LAMBDA_FUNCTION_NAME` overrides in each env stack; the detail is in `.claude/rules/infra.md`.
- **Repository rulesets** (`gh api repos/DataCrusade1999/supreme-enigma/rulesets`; classic branch protection is unused) — all three have a repository-admin bypass, so they stop accidents and other people, not the owner:
  - `permanent-branches`: no deletion and no force-push on `dev`, `stage` and `main`.
  - `stage-promotion-prs`: `stage` changes only through a PR, merged with `--merge`, all review threads resolved, and the `Tests` and `promotion-guard` checks green. A docs-only promotion gets no `Tests` run (see CI minutes below), so it can only merge with `gh pr merge <N> --merge --admin`.
  - `release-tags`: `v*` tags can be created but never moved or deleted.
  - **`main` has no PR or required-check rule, deliberately.** The `release` job pushes the changelog commit straight to `main` with `GITHUB_TOKEN`, and GitHub Actions can only be a ruleset bypass actor on an organization-owned repo, so such a rule would break every release. The PR-only flow into `main` is convention.
- `deploy.yml`'s `deploy` job (Lambda image build, push, `update-function-code`) runs on a push only when that push's last commit touches `lambda/` or `deploy.yml`; `workflow_dispatch` always rebuilds. **A dispatch on `main` also cuts a release** for a run that shipped nothing. A failed lambda `deploy` that nobody reruns leaves the Lambda stale: rerun it with `gh run rerun <id> --failed` (`docs/runbooks/stale-lambda-recovery.md`). Gating detail and the ECR tag check are in `.claude/rules/ci.md`.
- **CI minutes.** GitHub bills each job rounded up to a whole minute, and September 2026 went over the 2,000 free minutes and blocked Actions for the rest of the month (#320). Three choices follow from that: (1) everything that gates `deploy`/`release` is one `test` job, not four parallel ones — split, a ~20s Trivy job still billed a full minute and two jobs each paid for `npm install`, which took a run from ~4.4 to ~10 billed minutes. Don't split it back for wall-clock time. (2) `test` is skipped on a push to `dev` unless `changes` reports `lambda=true`: the PR already ran it, and `deploy` is the only thing on that push that needs it. A direct push to `dev` (the no-PR flow below) therefore reaches the dev deployment untested unless it touches `lambda/`; the `dev → stage` PR is the first run that covers it. `stage` and `main` pushes always run it. (3) `deploy.yml`'s `pull_request` trigger has `paths-ignore` for `docs/**`, `.claude/**` and `**.md`, so a docs-only PR — including a `chore/changelog-sync-*` PR whose diff is only `CHANGELOG.md` — gets **no CI run at all**. That is expected, not a missing check. `summary` runs only when `e2e-cross-os` did, since on any other run `test` writes the same tables itself.
- **`promotion-guard`** (its own workflow, no path filter) fails a PR into `stage` or `main` when the last release tag isn't an ancestor of the head branch, which means the `chore/changelog-sync-*` PR is unmerged or was squashed. It is a required check on `stage` (`stage-promotion-prs`) but only a red X on `main`: don't merge past it on either; merge the sync PR into `dev` with `--merge` first. How the check works is in `.claude/rules/ci.md`.
- The `release` job tags and publishes a GitHub Release on every successful push run on `main`; the bump comes from Conventional Commit prefixes since the last tag (`feat:` → minor, `!`/`BREAKING CHANGE:` → major, else patch).
- `CHANGELOG.md` (Keep a Changelog format): add entries under `## [Unreleased]` by hand, in the same PR as the change. The `release` job does the rest: it renames `[Unreleased]` to the new version on `main`, opens a `chore/changelog-sync-vX.Y.Z` PR into `dev`, then tags. That sync PR must be merged promptly with `--merge` — its mechanics, recovery path and CI-approval gate are in the `merging-a-pr` skill.

## Merging a PR

**Before merging any PR, invoke the `merging-a-pr` skill and follow it end to end** — CI gates, both review bots, finding triage, thread resolution. Do not merge on a partial signal, and do not merge two PRs concurrently. These rules hold even if the skill is not loaded:

- **A release-readiness verdict other than `change approved` is a hard stop.** Treat a commit-status `state` other than `success`, or a description without `change approved`, as blocked: report it and wait for a human decision.
- **The devops agent doesn't review PRs on its own while the repo is public** (AWS limits automated reviews to private repositories; #361). A PR with no release-readiness status has usually had no review started. Request one with `create_release_readiness_review` and gate on the report's `recommendedAction`: only `Standard Deployment` counts as approval, and anything else, `Deploy with Caution` included, is the same hard stop. The skill has the steps.
- **Merge method by PR kind:** feature/fix → `dev`: `gh pr merge <N> --squash --delete-branch`. `chore/changelog-sync-*` → `dev`: `--merge --delete-branch`, **never `--squash`**. Promotion `dev → stage` / `stage → main`: `--merge`, **never `--squash` and never `--delete-branch`**.
- **Absent test jobs on a sync PR mean gated, not skipped** — approve the run and wait; never merge on a green Vercel check alone. The exception: a PR whose diff is only docs/`*.md` (including a `CHANGELOG.md`-only sync PR) gets no CI run by design — check `gh pr diff <N> --name-only` before treating a missing run as gated.
- **For any PR touching `infra/`, read the plan the `Terraform` workflow posted on the PR:** each stack must say `No changes` or exactly the intended diff, with no `⚠ destroys or replaces` line you did not intend. A local plan is the fallback when the workflow cannot run.
- **Merge `lambda/`-touching PRs one at a time** — concurrent `deploy` jobs fail with `ResourceConflictException`.

## Project management

Work is tracked as GitHub issues, labeled `area: *` (bgm-looper/bgm-extractor/portfolio/infra/testing) and `priority: high/medium/low`, and triaged on the [BGM Looper Roadmap](https://github.com/users/DataCrusade1999/projects/4) project board (`Status`: Todo/In Progress/Done — GitHub's built-in workflows auto-update it on item-added/closed/PR-merged, already enabled by default, nothing to configure). Multi-phase initiatives (e.g. the portfolio UI overhaul) get an `epic`-labeled tracking issue with a task list linking each phase's issue. New issues should use the templates under `.github/ISSUE_TEMPLATE/` (feature/bug/chore — blank issues are disabled).

**File the issue before starting the work, and close it from the PR with `Closes #N`.** This is a precondition, not a convention — it holds for every authored PR into `dev` regardless of size: features, fixes, docs, chores, one-line changes. The issue is where the *why* lives; a PR alone records what changed but not what prompted it, and a change too small to describe in an issue is usually too small to need a PR. Two categories are exempt because they cannot comply: **promotion PRs** (`dev → stage`, `stage → main`), which carry work whose issues already exist, and **bot PRs** (dependabot, `chore/changelog-sync-*`), which are opened before anyone sees them.

**An explicit direct-push instruction replaces the issue-and-PR flow.** If the user says to push straight to dev ("commit and push to origin dev", "no issue and no PR"), commit on `dev` and push to `origin/dev` without filing an issue or opening a PR, and do not ask whether they want one. The issue-first rule applies only when a PR is being opened. The instruction covers the work it was given for; without it, the default flow applies.

**`Closes #N` only fires when the PR merges into the default branch.** `dev` is the default branch here, so a PR into `dev` closes its issue on merge, while the same keyword on a `dev → stage` or `stage → main` promotion is silently inert — GitHub only honours it on the default branch. That means an issue closes when the fix reaches `dev`, not when it reaches production. That is the right moment to close it, but say so rather than waiting for a close that will never come, and do not write `Closes #N` on a promotion PR expecting it to work. A design-spec-and-plan pair existing under `docs/superpowers/` does not imply an issue exists yet or vice versa — check the project board for current status, not just the docs.

## Scope of a fix

When the user names one instance of a problem (one URL showing `%2F`, one button missing the pointer cursor), assume they want the class fixed. Search for the other instances of that same problem and fix them in the same change, or list the ones you left and why. Do not touch code that is not an instance of the named problem.

## Writing

Remove all mannered prose — in docs, specs, plans, commit messages, PR descriptions, and blog content. Say the thing plainly; no throat-clearing, no rhetorical flourishes, no summary paragraphs restating what was just said.

## Gotchas

- **Vercel builds a push only when its *last* commit touches `web/` or `content/`.** `ignore_command` runs `git diff --quiet HEAD^ HEAD`, so a push that ends with a docs-only commit skips the preview even when earlier commits in it changed `web/`. #353's web code never had a preview; its first Vercel run was the `dev` deployment after the merge. To get a preview of web changes, push them before the docs commit, or push a commit that touches `web/` last.
- **Always pass both `--profile personal` and `--region us-east-1`, explicitly, on every manual `aws` CLI command in this project.**
  - Profile: it's a different AWS account (`223376380711`) than whatever the shell's default/`admin` profile points to (`688799538039`, unrelated account with no CE/Pricing/S3-list access) — this repo's actual infra (S3 buckets, ECR repo, Lambda) lives under `personal`. `.claude/settings.json` also sets `AWS_PROFILE=personal` for Claude Code sessions (that's what fixes the AWS MCP plugins, which pass no `--profile`) — but pass the flag anyway, since a plain shell doesn't inherit it.
  - Region: the `personal` profile's own configured default region is `ap-south-1` (Mumbai — presumably this user's general default elsewhere), but this project's real resources live in `us-east-1`. Terraform is never affected (its provider hardcodes `region = var.aws_region`, defaulting to `us-east-1`) — only raw `aws` CLI calls are at risk. Omitting `--region` silently queries `ap-south-1` and returns a misleading `ResourceNotFoundException`/`RepositoryNotFoundException` that looks like the resource is missing, when it's actually just the wrong region.
- S3 objects: uploads under `uploads/`, processed output under `outputs/` (same key, prefix swapped), all auto-expire after 1 day. Presigned URLs expire after 300s.
