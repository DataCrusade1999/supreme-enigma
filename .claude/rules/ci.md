# `.github/` — CI workflows and scripts

The branch model, the CI-minutes rules and the merge rules live in the root `CLAUDE.md`. This file is the per-workflow detail.

- **`deploy` gating.** `.github/workflows/deploy.yml`'s `deploy` job (Lambda image build + push to ECR + `update-function-code`) only runs on a push when the diff against the previous commit touches `lambda/` or `deploy.yml` itself — a `changes` job does a plain `git diff --quiet` (no third-party action, matches this repo's preference for hand-rolled scripting over marketplace actions) and gates `deploy` on its output. This avoids rebuilding and redeploying an identical Lambda image on every `web/`-only push. `workflow_dispatch` bypasses the check entirely and always rebuilds — the manual escape hatch if the Lambda is ever suspected to be stale. Known trade-off: if a lambda-touching push's `deploy` fails (as happened once from a transient `johnvansickle.com` network timeout) and nobody reruns it, a later push that doesn't touch `lambda/` will still skip `deploy` and leave the Lambda on the last successful image — recovery is manual, not automatic. Prefer `gh run rerun <id> --failed` on the run that failed: it rebuilds at the commit that should have deployed. **`workflow_dispatch` on `main` also cuts a release** — its `if:` treats the dispatch event as satisfying the `changes` gate, and `Determine next version` defaults `BUMP=patch` with no qualifying commits, so a dispatch rewrites `CHANGELOG.md` on `main`, opens a sync PR and tags a version for a run that shipped nothing. That is fine on `dev`/`stage`, where `release` never runs. Detection, both recovery paths and the caveat in full are in `docs/runbooks/stale-lambda-recovery.md`.
- The ECR repo is `image_tag_mutability = "IMMUTABLE"` (tags are `main/dev/stage-<sha>`, deterministic per commit) — so `deploy.yml`'s build/push step first checks `aws ecr describe-images` for that exact tag and skips build+push if it already exists. Without this check, retrying a failed `deploy` job (or `workflow_dispatch`) on the same commit would re-push the same tag and hard-fail with `ImageTagAlreadyExistsException` — this is the same retry pattern the "transient `johnvansickle.com` timeout" incident below relied on, so the idempotency check isn't optional.
- **`promotion-guard` refuses a promotion whose merge base predates the last release heading.** It lives in its own workflow, `.github/workflows/promotion-guard.yml`, with no path filter, so a docs-only promotion still gets checked. It runs on every `pull_request` into `stage` or `main` and asserts the most recent `v*` tag reachable from `main` is an ancestor of the PR's head branch. That is false exactly when the `chore/changelog-sync-*` PR has not been merged yet, or was merged with `--squash` — the two ways the next promotion corrupts `CHANGELOG.md`, either duplicating the version heading or splicing un-shipped entries in under it without a conflict. The check deliberately uses `github.event.pull_request.head.sha`, not `HEAD`: on a `pull_request` event `HEAD` is the synthetic merge commit, whose base parent already contains the tag, so it would pass for free. It asserts the *tag* is an ancestor, not that `main` is an ancestor of `dev` — the latter is false on every healthy run, since a promotion's merge commit lives only on the target branch. Branch protection is not enforced here, so this is a red X, not a hard block; do not merge past it. The fix is to merge the sync PR into `dev` first, with `--merge`.
- `release`'s `if:` explicitly checks `needs.test.result == 'success'` and `needs.deploy.result != 'failure'`/`!= 'cancelled'` rather than relying on GitHub Actions' default `if: success()` gating — a custom `if:` on a job replaces that default entirely, and `deploy` being *skipped* (no lambda changes, by design) must still let `release` run, while `deploy` actually *failing* must not.
- Job summaries are rendered by four dependency-free Node scripts under `.github/scripts/`, all sharing `summary-lib.mjs` (fence escaping, ANSI stripping, blob links, duration formatting) and all unit-tested by the `test` job's `node --test ".github/scripts/*.test.mjs"` step — **a change to any of them has to keep its `*.test.mjs` green, and that step gates `deploy`/`release` like any other.** `unit-summary.mjs` renders Vitest (`web/vitest-results.json`); `security-summary.mjs` renders Trivy's **JSON** (`trivy-results.json`) and writes the same markdown to `trivy-summary.md` for the artifact; `run-summary.mjs` renders the whole-run table from `toJSON(needs)` in the `summary` job. Report paths are CLI args from `deploy.yml`, so changing a reporter's `outputFile` — or Trivy's `format`/`output` — means updating the workflow too.
- **Playwright results reach the summary through artifacts.** `$GITHUB_STEP_SUMMARY` is per job, and the Linux run (in `test`) and the Windows/macOS legs (`e2e-cross-os`) are separate jobs, so each uploads its report as the artifact `playwright-results-${{ runner.os }}`, with the file inside the zip under a `playwright-results-<OS>/` directory. On a PR into `main` the `summary` job downloads all of them (`pattern: playwright-results-*`, **with** `merge-multiple: true`) and renders one spec × OS table via `e2e-summary.mjs`; on every other run `test` points the same script at its own `web/staging` directory. The OS has to be inside the zip, not only in the artifact name: `download-artifact` v5+ extracts a pattern download flat whenever it matches exactly one artifact and nests per artifact name only when it matches several, so relying on the artifact name gives `e2e-summary.mjs` two different layouts and it silently rendered `No Playwright result artifacts found` on the single-artifact one. Both upload steps set `overwrite: true` because uploaded artifacts are immutable and `gh run rerun --failed` re-uploads the same name. Every summary step that emits a source link takes `HEAD_SHA: ${{ github.event.pull_request.head.sha || github.sha }}` in its `env:` — on a `pull_request` event `github.sha` is the synthetic merge commit, whose blob URLs are not reachable from the PR. The `summary` job gates nothing, and its download step is `continue-on-error: true` so a cancelled leg produces a summary that says so rather than a red job.
- `.github/workflows/deploy.yml`'s `release` job auto-tags and creates a GitHub Release (`gh release create --generate-notes`) on every successful push-triggered run on `main`. Version bump is derived from Conventional Commit prefixes since the last tag (`feat:` → minor, `!`/`BREAKING CHANGE:` → major, else patch).
