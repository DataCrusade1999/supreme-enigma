# `infra/` — Terraform

Command and the per-branch resource layout live in the root `CLAUDE.md` (Commands, Branching & releases). This file is the per-file detail.

- **All three Lambda resources in `environments.tf` have `lifecycle { ignore_changes = [image_uri] }`** — do not remove this. CI updates the deployed Lambda image via `aws lambda update-function-code`; Terraform intentionally doesn't manage `image_uri` after creation.
- **Bootstrap order matters**: (1) apply `infra/bootstrap` once, (2) `terraform apply -target=aws_ecr_repository.looper` in `infra/main` (image must exist before the Lambda resource can be created), (3) apply IAM/exec-role resources, (4) push to `main`/`dev`/`stage` so CI builds+pushes each branch's image, (5) final `terraform apply` creates the Lambda functions + Vercel project. Step 5's `image_uri` for each function is a fixed tag from `var.bootstrap_image_tag_main`/`_dev`/`_stage` in `variables.tf` (defaults point at whatever tags were live as of 2026-08-06) — **before a from-scratch recreate** (e.g. after the kill-switch `terraform destroy`), update these to tags that branch's CI has actually pushed (`aws ecr describe-images --repository-name bgm-looper-lambda --profile personal --region us-east-1`). Because of the `ignore_changes` above, these vars are only consulted at creation time — deliberately a fixed tag per branch rather than a dynamic "most recently pushed" lookup, since the latter isn't branch-aware (could bootstrap `main`'s Lambda with a `dev` image) and forces every `terraform plan` to read ECR even when unrelated to Lambda, hard-failing if the repo is ever empty.
- **Terraform never reads `AWS_PROFILE`**: `providers.tf` sets `profile = var.aws_profile` (default `"personal"`) and `backend.tf` hardcodes the literal `"personal"`. CI sets neither — it uses env-var credentials only.
- **Web Analytics and Speed Insights are enabled by a dashboard toggle, not by Terraform.** The `vercel/vercel` provider has no attribute for either, so `<Analytics />` and `<SpeedInsights />` being mounted in `app/app/layout.tsx` is only half of it — the collection toggles are manual and, like the `KEYSTATIC_*` vars below, will not come back on a from-scratch recreate. Silence in the dashboard after a rebuild means the toggle, not the code. Both are also team-wide quotas that preview deployments draw down: 50,000 analytics events/month and 10,000 Speed Insights events per rolling 30 days, shared across `main`, `dev` and `stage`.
- **`BUTTONDOWN_API_KEY` is deliberately NOT managed here — set by hand in the Vercel dashboard, and staying that way.** `grep BUTTONDOWN infra/main/*.tf` is empty on purpose. It was created by hand when the newsletter shipped (#130) and is live on `production` and `preview`; the owner's decision (2026-09-14) is to leave it alone rather than adopt it into state. Bringing it under Terraform would mean `terraform import`-ing a live secret per target and carrying its plaintext in the gitignored `terraform.tfvars` — a plan run against the existing project confirmed the config wants to *create* the variable, so a plain apply would have collided with or duplicated the one already there. Not worth that for a key that is set once and never rotated on a schedule.

  What this costs, so nobody rediscovers it the hard way:

  - A from-scratch recreate (e.g. after the kill-switch `terraform destroy`) produces a project **without** this variable. Newsletter sending is then broken until it is re-added by hand, exactly like the three `KEYSTATIC_*` vars below.
  - `terraform plan` will never report it missing, because Terraform does not know it exists.

  The failure is at least legible now: `/tools/newsletter-admin` renders `BUTTONDOWN_API_KEY is not set` per issue rather than the old `Status unknown`, which was indistinguishable from "nothing has been sent yet" (`app/lib/buttondown.ts`'s `isButtondownConfigured()`, checked once before the fan-out). `POST /api/newsletter/send` fails closed with a 502 — deliberate, since refusing to send beats sending twice. The public `/newsletter` pages and the subscribe form never touch the key; they post straight to Buttondown.

- **The three `KEYSTATIC_*` Vercel env vars are not managed here** (`grep KEYSTATIC infra/main/*.tf` is empty) — unlike every other Vercel env var in this project they were set by hand in the Vercel dashboard, so a from-scratch recreate produces a Vercel project whose builds fail until they're re-added manually.
- **Preview deployments are public.** `vercel_project.looper` sets `vercel_authentication = { deployment_type = "none" }`, so the `dev` and `stage` URLs are reachable by anyone who has them — only `main`'s content is meant to be public, but the preview URLs are unguessable rather than protected. This was a deliberate downgrade from Vercel's default `standard_protection`: the AWS DevOps Agent's UI release testing cannot get through Vercel Authentication (see `docs/aws-devops-agent.md`). The gated parts of the app — `/tools/bgm-looper`, `/api/looper`, `/keystatic` — are behind `APP_PASSWORD` in `app/lib/route-gate.ts` independently of Vercel, so what this exposes is the public portfolio pages, which are already public on production. `vercel_project_protection_bypass.automation` is still provisioned as a token for any automation that *does* handle headers properly (Playwright sets `x-vercel-protection-bypass` cleanly); read it with `terraform output -raw protection_bypass_secret`, rotate with `terraform apply -replace=vercel_project_protection_bypass.automation`. Note the provider exposes the bypass as its own resource, not as an attribute on `vercel_project`.
- **`infra/bootstrap` has no persisted state.** It is applied once by hand, has no remote backend, and `*.tfstate` is gitignored — so on any fresh machine `terraform apply` there proposes re-creating the existing `aws_s3_bucket.tf_state` and hard-fails with `BucketAlreadyOwnedByYou`. Apply individual resources with `-target` (e.g. `terraform apply -target=aws_s3_account_public_access_block.account`, which is how the account PAB was applied on 2026-09-12) rather than a bare apply. Reconciling properly would mean `terraform import`-ing the four `tf_state` resources first, which buys little while the state file remains local and gitignored.
- **`aws_s3_account_public_access_block.account` lives in `infra/bootstrap/`, not `infra/main/`** — deliberately. `terraform destroy` in `infra/main` is the documented kill switch, and an account-wide guardrail has to outlive it; putting it in `main` would mean tearing the app down also removed the backstop for any bucket created afterwards. It is account-scoped, so it affects every bucket in `223376380711`, including `magma-learning-tfstate` — verified safe when added (2026-09-12): all five buckets already had their own per-bucket PAB, no bucket policy, no public ACL grant, no website hosting.
- **`vercel_firewall_config.looper` spends scarce Hobby-plan slots.** The plan allows **one** WAF rate-limit rule and **three** custom rules per project in total; the `/api/login` rule uses one of each. A second rate-limit rule cannot be added without upgrading or removing this one. The firewall config is project-level, so it applies to preview deployments as well as production. Window length is capped at 600s on Hobby (Enterprise gets 1hr), which is why the rule uses exactly that.
- **There is deliberately no `reserved_concurrent_executions` anywhere in `infra/main/*.tf`, and there cannot be.** This account's Lambda concurrency quota (`L-B99A9384`) is **10**, not the default 1,000, and AWS caps a reservation at "unreserved account concurrency minus 100" — so any non-zero value is rejected outright. Verified against the live account on 2026-09-16: `put-function-concurrency 0` returns `{"ReservedConcurrentExecutions": 0}`, `2` fails with `InvalidParameterValueException: ... decreases account's UnreservedConcurrentExecution below its minimum value of [10]`. Issue #154 proposed `reserved_concurrent_executions = 2` on both Lambda resources; it would have failed at apply. Don't re-derive it — if the cap is ever wanted, the quota increase comes first.

  What stands in for it is `aws_cloudwatch_metric_alarm.lambda_invocation_rate` in `environments.tf` (one per function, `for_each` over `local.all_lambda_function_names`): `Invocations` Sum > 50 per five minutes, to the `bgm-looper-budget-alerts` SNS topic. **`Invocations`, not `ConcurrentExecutions`** — concurrency is already hard-capped at 10 by the quota, so what is unbounded is how many times over that ceiling gets reused, which a concurrency alarm would never see. `treat_missing_data = "notBreaching"` is load-bearing: Lambda emits no datapoint when idle, and without it every alarm sits in `INSUFFICIENT_DATA` forever instead of reaching `OK`.

  **`aws_sns_topic_policy.budget_alerts` has to name `cloudwatch.amazonaws.com` explicitly.** That resource *replaces* SNS's default topic policy, so a publisher not listed there is denied — the alarm would still transition to `ALARM` and simply notify nobody. Same silent-failure shape as an unconfirmed email subscription below. Any future publisher to this topic needs its own statement.

- **A green CI `test` says nothing about `infra/`** — there is no `validate`, `fmt -check`, or `plan` anywhere in `deploy.yml`. For any PR touching `infra/`, run `terraform plan` in a scratch worktree against real state before merging and confirm `No changes.`
- **`terraform plan` cannot see a deleted or unconfirmed SNS email subscription, and reports `No changes` regardless.** `aws_sns_topic_subscription.budget_alerts_email` is an `email` protocol subscription, which nothing in Terraform can confirm — confirmation happens when a human clicks the link AWS mails out. The provider does not reconcile the subscription's real state on refresh, so a subscription that is `PendingConfirmation`, or one that has been unsubscribed entirely, still plans clean. It will never self-heal and never warn. **`No changes` is therefore not evidence the budget can reach anyone** — the `$5` `bgm-looper-monthly-cap` budget keeps evaluating and silently notifies nobody.

  Verify against the API instead, never against the plan or the absence of an email:

  ```bash
  aws sns get-topic-attributes \
    --topic-arn arn:aws:sns:us-east-1:223376380711:bgm-looper-budget-alerts \
    --profile personal --region us-east-1 \
    --query 'Attributes.{confirmed:SubscriptionsConfirmed,pending:SubscriptionsPending}'
  ```

  `confirmed: "1"` is the healthy state. In `list-subscriptions-by-topic`, the `SubscriptionArn` field doubles as the status: a real `arn:…` means confirmed, while the literal strings `PendingConfirmation` and `Deleted` mean it is not. `ConfirmationWasAuthenticated: false` is normal and not a fault — it only records that the link was clicked rather than an authenticated API call being made.

  This happened for real on 2026-09-13: the subscription was confirmed and then immediately unsubscribed (CloudTrail shows no `Unsubscribe` from any IAM or root principal, because the confirm and unsubscribe links are unauthenticated SNS endpoints that carry no identity — most likely the unsubscribe link on the confirmation-success page was followed, by a click or a mail-client prefetch). Clicking **Resubscribe** in the deactivated email revived the *same* subscription ARN, so Terraform state stayed truthful and no `-replace` was needed. If a future recreate is ever needed: `terraform apply -replace=aws_sns_topic_subscription.budget_alerts_email`. To prove delivery end to end rather than inferring it, `aws sns publish --topic-arn <arn> --subject … --message …` costs nothing and lands one email.
