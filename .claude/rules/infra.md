# `infra/` — Terraform

Command and the per-branch resource layout live in the root `CLAUDE.md` (Commands, Branching & releases). This file is the per-file detail.

Six stacks, six states, in three accounts (#397, spec `docs/superpowers/specs/2026-10-17-nonprod-accounts-design.md`):
- production, 223376380711, profile `personal`: `infra/shared` and `infra/envs/main` (which calls `infra/modules/environment` once)
- dev, 624586968135, profile `personal-dev`, and stage, 792682047320, profile `personal-stage`: `infra/nonprod/<env>/account` (through `infra/modules/nonprod-account`) and `infra/nonprod/<env>/env` (through `infra/modules/nonprod-env`, which calls `infra/modules/environment`)

Unless a bullet says otherwise, production's resources below live in `infra/shared`, except the bucket, Lambda function, invocation alarm and the `S3_BUCKET_NAME`/`LAMBDA_FUNCTION_NAME` env vars, which are in `infra/envs/main`; dev's and stage's equivalents are in their `account` and `env` stacks. Run the `terraform output`, `-replace` and `untaint` examples below from the directory of the stack that owns the resource, under that account's profile.

- **The Lambda resource in `infra/modules/environment/main.tf` (one per env stack: `envs/main` and both nonprod `env` stacks) has `lifecycle { ignore_changes = [image_uri] }`** — do not remove this. CI updates the deployed Lambda image via `aws lambda update-function-code`; Terraform intentionally doesn't manage `image_uri` after creation.
- **Bootstrap order matters**: (1) apply `infra/bootstrap` once per account (workspace `default` for production, `dev`/`stage` with `-var aws_profile=personal-<env>`), (2) `terraform apply -target=aws_ecr_repository.looper` in `infra/shared` (image must exist before a Lambda resource can be created), (3) apply the rest of `infra/shared`, and each nonprod `account` stack in two passes (the WebAuthn bullet below), (4) push to `main`/`dev`/`stage` so CI builds and pushes each branch's image into its own account's ECR, (5) apply `infra/envs/main`, `infra/nonprod/dev/env`, `infra/nonprod/stage/env` — each creates its Lambda function, bucket and env vars. Teardown is the reverse: in each account the env stack, then its base stack, with production's `shared` last since it owns the Vercel project. Step 5's `image_uri` for each function is the fixed `bootstrap_image_tag` in `infra/envs/main/main.tf` and `infra/nonprod/<env>/env/main.tf` (the tag live at that stack's first apply) — **before a from-scratch recreate** (e.g. after the kill-switch `terraform destroy`), update these to tags that branch's CI has actually pushed (`aws ecr describe-images --repository-name bgm-looper-lambda --profile <account's profile> --region us-east-1`). Because of the `ignore_changes` above, the tag is only consulted at creation time — deliberately a fixed tag per branch rather than a dynamic "most recently pushed" lookup, since the latter isn't branch-aware (could bootstrap `main`'s Lambda with a `dev` image) and forces every `terraform plan` to read ECR even when unrelated to Lambda, hard-failing if the repo is ever empty.
- **Terraform reads `AWS_PROFILE`; export the stack's profile before any local run**: `personal` for `infra/shared` and `infra/envs/main`, `personal-dev` or `personal-stage` for `infra/nonprod/<env>/*`. No backend block names a profile and `var.aws_profile` defaults to `null`, so both the backend and the provider use the environment's credentials: `AWS_PROFILE` on a workstation, and OIDC role credentials once Terraform runs in CI (phase 3 of the state-split spec, `docs/superpowers/specs/2026-10-01-terraform-state-split-design.md`). Every provider sets `allowed_account_ids` to its one account, so a nonprod stack run with the repo's default `AWS_PROFILE=personal` fails with `AWS account ID not allowed: 223376380711` before changing anything. All three profiles are IAM Identity Center on the personal organization's `personal-org` SSO session (`AdministratorAccess` permission set, 4-hour session), not access keys: run `aws sso login --profile personal` first (one login covers all three), and again whenever the CLI or Terraform reports an expired SSO session or token.
- **There are no IAM users and no long-lived access keys in this project** (#155, 2026-09-16). Every identity is a federated role assumed through OIDC, and `grep -rn 'aws_iam_user\|aws_iam_access_key' infra/shared infra/envs infra/nonprod infra/modules --include=*.tf` is empty on purpose:
  - `aws_iam_role.ci_deploy` — one per account, assumed by `deploy.yml`'s `deploy` job via `role-to-assume` (`deploy.yml` picks the account's role ARN per branch). That job needs `permissions: id-token: write` **and** `contents: read`: a job-level block replaces the repo default outright rather than adding to it, so omitting `contents: read` breaks `actions/checkout`.
  - `aws_iam_role.vercel` — assumed by the app through `awsCredentials()` in `web/lib/aws.ts`, which reads `APP_AWS_ROLE_ARN`. The variable is deliberately *not* named `AWS_ROLE_ARN`: the SDK's default credential chain reads that name itself and would attempt web-identity resolution from a token file that does not exist on Vercel. Same collision `APP_AWS_REGION` avoids.
  - **One Vercel role per account, chosen by target** (#333, #397): production deployments assume `bgm-looper-vercel` in 223376380711; dev's preview deployments assume `bgm-looper-vercel-preview` in 624586968135 and stage's the role of the same name in 792682047320. `APP_AWS_ROLE_ARN` is set for `production` in `infra/shared`, and for `preview` (dev, bare) and `preview` + `git_branch = "stage"` in each nonprod `env` stack. Each env stack attaches its own `bgm-looper-vercel-<env>` policy (its bucket's audio and News Desk prefixes, and invoke on its own Lambda); each environment's resume grant is on its own bucket (`aws_iam_role_policy.vercel_resume` in `infra/shared` for production, in `infra/modules/nonprod-env` for dev and stage). **A feature's new grant goes in `aws_iam_role_policy.vercel` in `infra/modules/environment/main.tf`, applied to `nonprod/dev/env` first.** Vercel's OIDC subject has only `production` and `preview`, so both nonprod accounts' preview roles trust the same `preview` subject; the account boundary is what keeps dev's deployments out of stage's resources: each deployment's `APP_AWS_ROLE_ARN` names its own account's role. A change to `APP_AWS_ROLE_ARN` reaches a deployment only through a new build — redeploy with "Use project's Ignore Build Step" unticked, or the ignore step cancels it.
  - **Per-environment Lambda exec roles**: `bgm-looper-lambda-exec-<env>`, in the module, each limited to its own bucket in its own account.

  **GitHub's `sub` is the immutable, ID-qualified form**, `repo:<owner>@<ownerId>/<repo>@<repoId>:ref:refs/heads/<branch>` — this repo has `use_immutable_subject: true`, GitHub's current default. `local.github_sub_prefix` (and `github_sub_prefix` in each `infra/nonprod/<env>/account/main.tf`) is copied verbatim from `gh api repos/DataCrusade1999/supreme-enigma/actions/oidc/customization/sub`; do not rebuild it out of `var.github_repo`. Vercel's is the documented `owner:<slug>:project:<name>:environment:<env>`, with only `production` and `preview` — Vercel has no per-branch environment, so `dev` and `stage` are both `preview`.

  **When a trust policy is wrong, STS says `Not authorized to perform sts:AssumeRoleWithWebIdentity` and names no claim.** CloudTrail is where the presented subject is legible: `LookupEvents` on `AssumeRoleWithWebIdentity` records it as `userIdentity.userName`. That is the diagnostic — the error message alone will not tell you whether `aud` or `sub` mismatched. Nothing alarms on these failures yet; see #166.
- **Web Analytics and Speed Insights are enabled by a dashboard toggle, not by Terraform.** The `vercel/vercel` provider has no attribute for either, so `<Analytics />` and `<SpeedInsights />` being mounted in `web/app/layout.tsx` is only half of it — the collection toggles are manual and, like the `KEYSTATIC_*` vars below, will not come back on a from-scratch recreate. Silence in the dashboard after a rebuild means the toggle, not the code. Both are also team-wide quotas that preview deployments draw down: 50,000 analytics events/month and 10,000 Speed Insights events per rolling 30 days, shared across `main`, `dev` and `stage`.
- **`BUTTONDOWN_API_KEY` is deliberately NOT managed here — set by hand in the Vercel dashboard, and staying that way.** `grep -rn BUTTONDOWN infra --include=*.tf` is empty on purpose. It was created by hand when the newsletter shipped (#130) and is live on `production` and `preview`; the owner's decision (2026-09-14) is to leave it alone rather than adopt it into state. Bringing it under Terraform would mean `terraform import`-ing a live secret per target and carrying its plaintext in the gitignored `terraform.tfvars` — a plan run against the existing project confirmed the config wants to *create* the variable, so a plain apply would have collided with or duplicated the one already there. Not worth that for a key that is set once and never rotated on a schedule.

  What this costs, so nobody rediscovers it the hard way:

  - A from-scratch recreate (e.g. after the kill-switch `terraform destroy`) produces a project **without** this variable. Newsletter sending is then broken until it is re-added by hand, exactly like the three `KEYSTATIC_*` vars below.
  - `terraform plan` will never report it missing, because Terraform does not know it exists.

  The failure is at least legible now: `/tools/newsletter-admin` renders `BUTTONDOWN_API_KEY is not set` per issue rather than the old `Status unknown`, which was indistinguishable from "nothing has been sent yet" (`web/lib/buttondown.ts`'s `isButtondownConfigured()`, checked once before the fan-out). `POST /api/newsletter/send` fails closed with a 502 — deliberate, since refusing to send beats sending twice. The public `/newsletter` pages and the subscribe form never touch the key; they post straight to Buttondown.

- **The three `KEYSTATIC_*` Vercel env vars are not managed here** (`grep -rn KEYSTATIC infra --include=*.tf` is empty) — unlike every other Vercel env var in this project they were set by hand in the Vercel dashboard, so a from-scratch recreate produces a Vercel project whose builds fail until they're re-added manually.
- **Preview deployments are public.** `vercel_project.looper` sets `vercel_authentication = { deployment_type = "none" }`, so the `dev` and `stage` URLs are reachable by anyone who has them — only `main`'s content is meant to be public, but the preview URLs are unguessable rather than protected. This was a deliberate downgrade from Vercel's default `standard_protection`: the AWS DevOps Agent's UI release testing cannot get through Vercel Authentication (see `docs/aws-devops-agent.md`). The gated parts of the app — `/tools/bgm-looper`, `/api/looper`, `/keystatic` — are behind `APP_PASSWORD` in `web/lib/route-gate.ts` independently of Vercel, so what this exposes is the public portfolio pages, which are already public on production. `vercel_project_protection_bypass.automation` is still provisioned as a token for any automation that *does* handle headers properly (Playwright sets `x-vercel-protection-bypass` cleanly); read it with `terraform output -raw protection_bypass_secret`, rotate with `terraform apply -replace=vercel_project_protection_bypass.automation`. Note the provider exposes the bypass as its own resource, not as an attribute on `vercel_project`.
- **`infra/bootstrap` has no persisted state.** It is applied once by hand, has no remote backend, and `*.tfstate` is gitignored — so on any fresh machine `terraform apply` there proposes re-creating the existing `aws_s3_bucket.tf_state` and hard-fails with `BucketAlreadyOwnedByYou`. Apply individual resources with `-target` (e.g. `terraform apply -target=aws_s3_account_public_access_block.account`, which is how the account PAB was applied on 2026-09-12) rather than a bare apply. Reconciling properly would mean `terraform import`-ing the four `tf_state` resources first, which buys little while the state file remains local and gitignored.
- **CloudTrail and GuardDuty belong to the personal AWS organization (DataCrusade1999/aws-org), not this repo.** The Control Tower organization trail records this account, and the audit account runs GuardDuty and emails findings for every member. This repo's own trail and findings rule were removed in #395, and the detector left its state in #394. `infra/shared/audit.tf` keeps only the old trail's bucket (`bgm-looper-cloudtrail-<account>`), which its 365-day expiry empties. The bucket has no `force_destroy`, so a kill-switch `terraform destroy` of `shared` stops at `aws_s3_bucket.audit` while logs remain: empty the bucket first, or `terraform state rm` it to keep the logs.
- **`aws_s3_account_public_access_block.account` lives in `infra/bootstrap/`, not `infra/shared/`** — deliberately. `terraform destroy` across the four stacks is the documented kill switch, and an account-wide guardrail has to outlive it; putting it in `shared` would mean tearing the app down also removed the backstop for any bucket created afterwards. It is account-scoped, so it affects every bucket in `223376380711`, including `magma-learning-tfstate` — verified safe when added (2026-09-12): all five buckets already had their own per-bucket PAB, no bucket policy, no public ACL grant, no website hosting. Dev's and stage's accounts got the same block from their `bootstrap` workspaces.
- **`vercel_firewall_config.looper` cannot hold a rate-limit rule.** The provider writes the whole firewall config with one PUT, and since late September 2026 Vercel's API refuses that PUT on Hobby whenever it contains a rate-limit rule (`forbidden - Rate limiting is not available for this plan`), even though the dashboard still edits one and Hobby's documented limit is one per project. A rate-limit rule here makes every apply of this resource fail. The old `/api/login` rule (#137) was removed in #306 — #294 had already deleted that route. If edge rate limiting is ever needed again, create it in the dashboard and leave it out of Terraform. Because the PUT replaces everything, anything set in the dashboard but missing from this resource is removed by the next apply, so declare every managed ruleset that is on (`ai_bots` and `bot_protection` today). The config is project-level, so it applies to preview deployments as well as production. Provider ≤5.17 reads `bot_protection` back only once it is already in state, so after an import the first plan shows it as an addition even when it is live.
- **There is deliberately no `reserved_concurrent_executions` anywhere under `infra/`, and there cannot be.** Production's Lambda concurrency quota (`L-B99A9384`) is **10**, not the default 1,000 (the quota is per account; check dev's and stage's before assuming the same), and AWS caps a reservation at "unreserved account concurrency minus 100" — so any non-zero value is rejected outright. Verified against the live account on 2026-09-16: `put-function-concurrency 0` returns `{"ReservedConcurrentExecutions": 0}`, `2` fails with `InvalidParameterValueException: ... decreases account's UnreservedConcurrentExecution below its minimum value of [10]`. Issue #154 proposed `reserved_concurrent_executions = 2` on both Lambda resources; it would have failed at apply. Don't re-derive it — if the cap is ever wanted, the quota increase comes first.

  What stands in for it is `aws_cloudwatch_metric_alarm.lambda_invocation_rate` in `infra/modules/environment/main.tf` (one per function, so one per env stack): `Invocations` Sum > 50 per five minutes, to that account's `bgm-looper-budget-alerts` SNS topic. **`Invocations`, not `ConcurrentExecutions`** — concurrency is already hard-capped at 10 by the quota, so what is unbounded is how many times over that ceiling gets reused, which a concurrency alarm would never see. `treat_missing_data = "notBreaching"` is load-bearing: Lambda emits no datapoint when idle, and without it every alarm sits in `INSUFFICIENT_DATA` forever instead of reaching `OK`.

  **`aws_sns_topic_policy.budget_alerts` has to name `cloudwatch.amazonaws.com` explicitly.** That resource *replaces* SNS's default topic policy, so a publisher not listed there is denied — the alarm would still transition to `ALARM` and simply notify nobody. Same silent-failure shape as an unconfirmed email subscription below. Any future publisher to this topic needs its own statement.

- **CI lints and plans every infra PR.** The `Terraform` workflow runs `fmt -check`, `tflint` (`infra/.tflint.hcl`), `validate` and a plan of the base branch's stacks (`.github/scripts/tf-stacks.sh plan`: `shared` and `nonprod/dev/*` into `dev`, `nonprod/stage/*` into `stage`, `envs/main` into `main`) on each PR, and posts the plans as one PR comment, rewritten on every run and marked incomplete when lint or plan failed. Read that comment before merging. The security scan is `deploy.yml`'s Trivy filesystem scan in the `test` job, which reads `infra/*.tf`; `terraform.yml` has no Trivy step of its own (#339 dropped a plan scan that duplicated it).
- **Terraform runs in CI** (#339, `.github/workflows/terraform.yml`; production's roles in `infra/shared/ci.tf`, dev's and stage's in `infra/modules/nonprod-account/iam.tf`). `.github/scripts/tf-stacks.sh` is the one routing table: which stacks each branch applies, and which account's role each stack assumes (`tf-as.sh`).
  - Production: `bgm-looper-tf-plan` (`ReadOnlyAccess` plus Verified Permissions reads; PRs and the weekly drift run) — every plan runs `-lock=false`, so it never writes a lock file. `bgm-looper-tf-apply-prod` applies `shared` on pushes to `dev` and `envs/main` on pushes to `main` (and manual runs of either), with IAM limited to `bgm-looper-*` names and the two OIDC providers, and is denied changes to the state bucket itself.
  - Dev and stage: each account has its own `bgm-looper-tf-plan` (trusted by PRs and `dev`, since drift runs from `dev` for every stack) and `bgm-looper-tf-apply` (trusted only by that environment's branch). The apply role has `AdministratorAccess`, bounded by the account: nothing in it trusts anything outside it, and the organization's deny-IAM-users SCP still applies.
  - **Production's apply role can't write S3 objects.** It gets `CreateBucket`, `PutBucket*`, `DeleteBucket*`, `PutLifecycleConfiguration` and `PutEncryptionConfiguration` on main's data bucket and the audit bucket, not `s3:*` (Trivy's AWS-0345 in the `test` job fails on `s3:*`). Terraform manages no objects today; a new `aws_s3_object`, or `force_destroy` on a bucket, needs a grant in `infra/shared/ci.tf` applied first, or CI's apply fails with `AccessDenied`.
  - One gap left in the nonprod scope (nonprod-accounts spec): the Vercel token is account-wide, so a nonprod apply can edit production's Vercel settings. Separate accounts closed the other one, the old `bgm-looper-tf-apply-nonprod` role's unconditioned `iam:PutRolePolicy` on the shared preview role.
  - **Destroy guard.** An apply whose plan deletes or replaces anything stops before applying and lists the addresses in the job summary. To apply it, run `gh workflow run terraform.yml --ref <branch> -f stack=<stack> -f confirm=apply-destroys` from the branch that owns the stack (`shared` and `nonprod/dev/*` on `dev`, `nonprod/stage/*` on `stage`, `envs/main` on `main`); a mismatched stack fails at `Resolve stacks`.
  - **Drift.** Every Monday 03:30 UTC (or `gh workflow run terraform.yml --ref dev -f stack=drift`; the plan role trusts only `dev` and PRs, so the job refuses any other ref) each stack is planned from the branch that applies it (`shared` from `dev`); drift opens or comments on the issue labelled `drift`, and a clean run closes it.
  - Inputs: repository secrets `TF_VAR_VERCEL_API_TOKEN`, `TF_VAR_APP_PASSWORD`, `TF_VAR_OPENROUTER_API_KEY`, `TF_VAR_GOOGLE_CLIENT_SECRET`; repository variables `TF_VAR_GITHUB_REPO`, `TF_VAR_ALERT_EMAIL`, `TF_VAR_GOOGLE_CLIENT_ID`. A rotated value in `terraform.tfvars` has to be set there too.
  - The repo setting that sends secrets and write tokens to fork-PR workflows must stay off: it is what keeps a fork PR from assuming the plan role.
  - Dependabot's own PRs are not planned (no secrets, no OIDC token); the owner-opened batch PR is.
  - Break-glass is a local plan and apply with `personal` credentials, as before. The kill switch stays local; CI never destroys a stack.
- **`terraform plan` cannot see a deleted or unconfirmed SNS email subscription, and reports `No changes` regardless.** `aws_sns_topic_subscription.budget_alerts_email` is an `email` protocol subscription, which nothing in Terraform can confirm — confirmation happens when a human clicks the link AWS mails out. The provider does not reconcile the subscription's real state on refresh, so a subscription that is `PendingConfirmation`, or one that has been unsubscribed entirely, still plans clean. It will never self-heal and never warn. **`No changes` is therefore not evidence the budget can reach anyone** — the `$5` `bgm-looper-monthly-cap` budget keeps evaluating and silently notifies nobody.

  Verify against the API instead, never against the plan or the absence of an email:

  ```bash
  aws sns get-topic-attributes \
    --topic-arn arn:aws:sns:us-east-1:223376380711:bgm-looper-budget-alerts \
    --profile personal --region us-east-1 \
    --query 'Attributes.{confirmed:SubscriptionsConfirmed,pending:SubscriptionsPending}'
  ```

  `confirmed: "1"` is the healthy state. In `list-subscriptions-by-topic`, the `SubscriptionArn` field doubles as the status: a real `arn:…` means confirmed, while the literal strings `PendingConfirmation` and `Deleted` mean it is not. `ConfirmationWasAuthenticated: false` is normal and not a fault — it only records that the link was clicked rather than an authenticated API call being made.

  This happened for real on 2026-09-13: the subscription was confirmed and then immediately unsubscribed (CloudTrail shows no `Unsubscribe` from any IAM or root principal, because the confirm and unsubscribe links are unauthenticated SNS endpoints that carry no identity — most likely the unsubscribe link on the confirmation-success page was followed, by a click or a mail-client prefetch). Clicking **Resubscribe** in the deactivated email revived the *same* subscription ARN, so Terraform state stayed truthful and no `-replace` was needed. If a future recreate is ever needed: `terraform apply -replace=aws_sns_topic_subscription.budget_alerts_email`. To prove delivery end to end rather than inferring it, `aws sns publish --topic-arn <arn> --subject … --message …` costs nothing and lands one email.
- **`vercel_dns_record` needs `team_id = local.vercel_team_id`.** The `vercel` provider sets no team, and every project-scoped resource works anyway because the project API resolves through the token's default team. The domains API does not: without an explicit `teamId` it answers `forbidden - You don't have access to "ashutosh-pandey.com"`, even though the token's default team owns the domain. Any new DNS record resource needs the attribute.
- **Changing any `asset` on `aws_cognito_managed_login_branding.web` replaces the resource**, and managed login serves no page while the client has no style. A replace whose create is rejected leaves the sign-in page down until an apply succeeds; this happened on 2026-09-29, when a header logo wider than 4:1 was refused (`Assets of SubType LOGO must have a width:height ratio between 1:1 and 4:1`). A `settings`-only change updates in place. The favicon has to be uploaded per colour mode like the logos: a `DYNAMIC` one is stored but never served. Cognito draws `PAGE_HEADER_LOGO` 40px high (at most 160px wide) and `FORM_LOGO` 60px high (at most 240px wide), so the SVGs under `branding/` are drawn at those sizes to render 1:1; `branding/generate/` rebuilds them and `branding.json` (its `README.md` has the command). The live page can lag an apply by a minute while Cognito rebuilds its theme stylesheet.
- **Cognito WebAuthn on a from-scratch apply.** `aws_cognito_user_pool.owner` sets `web_authn_configuration.relying_party_id` to its own custom domain, and Cognito rejects that until `aws_cognito_user_pool_domain.custom` exists — which Terraform creates *after* the pool. So a fresh apply (e.g. after the kill-switch `terraform destroy`) creates the pool, then fails with `InvalidParameterException: RelyingPartyId cannot be reserved domain other than User Pool's prefix domain` and taints it. Re-running loops. Recovery, as done on 2026-09-28: `terraform untaint module.auth.aws_cognito_user_pool.owner`, apply with `webauthn_enabled = false` on the `module "auth"` call (which leaves the `web_authn_configuration` block out), then set it back to `true` and apply. Omitting only `relying_party_id` applies cleanly but leaves the relying party empty (`get-user-pool-mfa-config` shows no `RelyingPartyId`), so do not settle for that form. Dev's and stage's pools come from the same module, so their `account` stacks take the same two passes on a fresh apply: `-var webauthn_enabled=false`, then a plain apply (how they were first built, Tasks 9 and 11 of the nonprod-accounts plan).
- **`infra/modules/auth/cedar/` is deployed by Terraform, not Vercel.** `infra/modules/auth/main.tf` loads the schema and one `aws_verifiedpermissions_policy` per `.cedar` file, filling `${pool}` with the user pool ID. The policy store is `STRICT`, so a policy that doesn't match the schema fails at apply; `web/lib/authz/policies.test.ts` runs the same files through `cedar-wasm` first. A change under `cedar/` doesn't trigger a Vercel build (the `ignore_command` allowlist is `web/` and `content/`) and doesn't need one.
- Vercel picks the right `S3_BUCKET_NAME`/`LAMBDA_FUNCTION_NAME` (and every other per-environment value: the role, Cognito, the policy store, the resume bucket) per branch via target- and `git_branch`-scoped env vars in each env stack (`vercel_target`/`vercel_git_branch` in `infra/envs/main/main.tf` and `infra/nonprod/<env>/env/main.tf`): `production` target → main's resources, bare `preview` target (the default for any branch) → dev's account, `git_branch = "stage"` override → stage's account.
- Each account's ECR repo holds only its own branch's images, and its lifecycle policy keeps the last 1 (tightened from 5 to cut storage cost). Trade-off: no rollback via ECR on a bad deploy — a fresh CI rebuild from git history is the recovery path.
- `vercel_project.looper` pins `git_repository.production_branch = "main"` explicitly in `shared.tf`, decoupled from GitHub's default branch — required precisely because the default branch is `dev`, not `main`.
- **`vercel_project.looper`'s `ignore_command` is an allowlist with `:(top)` pathspecs.** `git diff --quiet HEAD^ HEAD -- ':(top)web' ':(top)content'`: a commit touching only `lambda/`, `infra/`, `docs/`, `CLAUDE.md` or `.github/` is skipped, and a new top-level directory that becomes build-relevant has to be added or it silently stops deploying. The `:(top)` prefix is needed because Vercel runs the command from `root_directory`: bare pathspecs resolved against `web/`, matched nothing, and skipped *every* build from #181 until #230 fixed it.
