# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

Per-area detail lives in `.claude/rules/` (`app.md`, `lambda.md`, `infra.md`), path-scoped so each loads only when you touch that project. Anything needed *before* opening a file — commands, branch/PR process, cross-cutting gotchas — stays here.

## Structure

Three independent sibling projects, no monorepo tooling (no workspaces/Turborepo/Nx):
- `app/` — Next.js 16 + React 19 + TypeScript frontend, deployed to Vercel (`root_directory = "app"` — only changes here trigger a Vercel deploy). Public portfolio pages (home/about/projects/resume/blog/contact) live in the `app/app/(site)/` route group and have no auth check at all. The gated areas are the BGM Looper tool (`app/app/tools/bgm-looper/`, `/api/looper/*`) and the Keystatic admin (`/keystatic`, `/api/keystatic/*`); `app/lib/route-gate.ts` is the single source of truth for what's gated.
- `lambda/` — Python 3.12 DSP pipeline (audio loop processing), packaged as a Lambda container image.
- `infra/bootstrap/` — Terraform, applied once manually, creates only the Terraform state S3 bucket. Never destroyed by the kill switch.
- `infra/main/` — Terraform, remote state, creates the per-branch audio S3 buckets and Lambda functions (three of each — see Branching & releases), the shared ECR repo, IAM users/roles, and the Vercel project.
- `content/` — repo root, sibling to `app/`: git-backed blog content managed by Keystatic (GitHub mode), separate from the hand-written `app/content/projects.ts`/`resume.ts` data files — see `docs/superpowers/specs/2026-08-01-portfolio-blog-design.md` for why.
- `docs/superpowers/specs/` and `docs/superpowers/plans/` — the design specs and TDD implementation plans this project was built from (one pair per phase: the original bgm-looper build, the portfolio-site restructuring, the blog, etc.); check here for the "why" behind existing decisions before assuming something is undocumented.
- `ARCHITECTURE.md` (repo root) — architecture + measured cost breakdown.
- No in-tree worktrees: the stray `.claude/worktrees/bgm-looper-impl/` and `.worktrees/portfolio-blog/` duplicate checkouts were removed 2026-09-11 (both branches were fully merged into `dev`), so `grep`/`find` from the repo root no longer hits duplicates. `.gitignore` still covers both paths — keep scratch worktrees out of the tree. The stale `C:/tmp2/stage-promote` registration was pruned 2026-09-13, so `git worktree list` is now clean; its `_tmp-promote-stage` branch still exists locally with 7 commits not in `origin/dev` (pruning removes only the worktree registration, never the branch).

## Commands

- App unit tests: `cd app && npm test` (= `vitest run`). **This is only half the CI gate** — CI's `test` job runs Vitest *and* Playwright and fails if either fails.
- App e2e tests: `cd app && npm run test:e2e` (= `playwright test`, specs in `app/e2e/`). Needs a one-time `npx playwright install chromium`. It builds and serves the app itself — see `.claude/rules/app.md`.
- App lint: `cd app && npm run lint` (ESLint via `eslint-config-next`, config in `eslint.config.mjs`).
- App dev: `cd app && APP_PASSWORD=test123 COOKIE_SECRET=devsecret npm run dev`.
- App build: `cd app && KEYSTATIC_GITHUB_CLIENT_ID=dummy KEYSTATIC_GITHUB_CLIENT_SECRET=dummy KEYSTATIC_SECRET=dummy npm run build` — see the Keystatic env var gotcha below; dummy values are fine for a local build, the real ones are only needed to actually authenticate against GitHub.
- Lambda tests: `cd lambda && .venv/Scripts/python -m pytest -q` on Windows (`.venv/bin/python -m pytest -q` on macOS/Linux). `pytest.ini` sets `pythonpath = src`. Deps live in `lambda/.venv` (local Python 3.13, CI 3.12), deliberately not the global interpreter — setup and the version rationale are in `.claude/rules/lambda.md`; re-run its `pip install` after any Dependabot bump.
- Terraform: run from `infra/main/` with `-var-file=terraform.tfvars`. That file is gitignored (`*.tfvars`) and has **five required variables, none with a default** — `vercel_api_token`, `app_password`, `github_repo`, `alert_email`, `openrouter_api_key` — so a fresh clone fails with `No value for required variable` until all five are set. `infra/main/terraform.tfvars.example` is the committed template; copy it across and fill it in. Bootstrap order, `ignore_changes`, and the profile gotcha are in `.claude/rules/infra.md`.

## Branching & releases

- Three permanent branches: `dev` → `stage` → `main`. `dev` is the GitHub default branch — new local branches and PRs target `dev` by default. Promote by opening a PR `dev → stage`, then `stage → main` once QA'd.
- Live URLs (see README's Environments table too): `main` → https://bgm-looper.vercel.app, `stage` → https://bgm-looper-git-stage-ashutosh-pandeys-projects-77cb3a00.vercel.app, `dev` → https://bgm-looper-git-dev-ashutosh-pandeys-projects-77cb3a00.vercel.app.
- `infra/main/*.tf` is split by shared-vs-per-branch, not by resource type: `shared.tf` holds the one-of-each resources used by all three branches (ECR repo, IAM exec role + service-account users, the Vercel project, env-agnostic secrets) — `environments.tf` holds the per-branch resources (each branch's S3 bucket, Lambda function, and the Vercel env var overrides that point at them).
- Each branch has its own full backend: separate Lambda functions (`bgm-looper-processor`, `-dev`, `-stage`), separate S3 buckets (`bgm-looper-audio-<account>`, `-dev-<account>`, `-stage-<account>`), one shared ECR repo with per-branch tag prefixes (`main-<sha>`, `dev-<sha>`, `stage-<sha>`; no `:latest` — dropped 2026-08-06 since it was unused by the actual deploy step and could be silently overwritten). `main`'s Lambda/bucket are the original resources (unrenamed, to avoid a destructive rename) — `dev`/`stage` are the `_env` for_each twins in `environments.tf`. All three share one IAM exec role, scoped to all three bucket ARNs.
- Vercel picks the right `S3_BUCKET_NAME`/`LAMBDA_FUNCTION_NAME` per branch via `git_branch`-scoped env var overrides in `environments.tf`: `production` target → main's resources, bare `preview` target (the default for any branch) → dev's resources, `git_branch = "stage"` override → stage's resources.
- ECR's lifecycle policy prunes each prefix independently (keep last 1 per `main`/`dev`/`stage`, tightened from 5 to cut storage cost) — a burst of `dev` pushes can't evict images `main` still needs. Trade-off: no rollback via ECR on a bad deploy — a fresh CI rebuild from git history is the recovery path.
- The ECR repo is `image_tag_mutability = "IMMUTABLE"` (tags are `main/dev/stage-<sha>`, deterministic per commit) — so `deploy.yml`'s build/push step first checks `aws ecr describe-images` for that exact tag and skips build+push if it already exists. Without this check, retrying a failed `deploy` job (or `workflow_dispatch`) on the same commit would re-push the same tag and hard-fail with `ImageTagAlreadyExistsException` — this is the same retry pattern the "transient `johnvansickle.com` timeout" incident below relied on, so the idempotency check isn't optional.
- `vercel_project.looper` pins `git_repository.production_branch = "main"` explicitly in `shared.tf`, decoupled from GitHub's default branch — required precisely because the default branch is `dev`, not `main`.
- Branch protection (PR-only merges, no force-push) on `stage`/`main` is **not enforced** — GitHub blocks branch protection/rulesets on private repos without Pro. Convention-only until upgraded or made public.
- `.github/workflows/deploy.yml`'s `deploy` job (Lambda image build + push to ECR + `update-function-code`) only runs on a push when the diff against the previous commit touches `lambda/` or `deploy.yml` itself — a `changes` job does a plain `git diff --quiet` (no third-party action, matches this repo's preference for hand-rolled scripting over marketplace actions) and gates `deploy` on its output. This avoids rebuilding and redeploying an identical Lambda image on every `app/`-only push. `workflow_dispatch` bypasses the check entirely and always rebuilds — the manual escape hatch if the Lambda is ever suspected to be stale. Known trade-off: if a lambda-touching push's `deploy` fails (as happened once from a transient `johnvansickle.com` network timeout) and nobody reruns it, a later push that doesn't touch `lambda/` will still skip `deploy` and leave the Lambda on the last successful image — `workflow_dispatch` is the fix in that case, not automatic.
- `release`'s `if:` explicitly checks `needs.test.result == 'success'` and `needs.deploy.result != 'failure'`/`!= 'cancelled'` rather than relying on GitHub Actions' default `if: success()` gating — a custom `if:` on a job replaces that default entirely, and `deploy` being *skipped* (no lambda changes, by design) must still let `release` run, while `deploy` actually *failing* must not.
- The `test` job pipes both runners' JSON reports through `.github/scripts/test-summary.mjs` into the job summary — the report paths (`app/vitest-results.json`, `app/playwright-results.json`) are passed as CLI args from `deploy.yml`, so changing a reporter's `outputFile` means updating the workflow too.
- `.github/workflows/deploy.yml`'s `release` job auto-tags and creates a GitHub Release (`gh release create --generate-notes`) on every successful push-triggered run on `main`. Version bump is derived from Conventional Commit prefixes since the last tag (`feat:` → minor, `!`/`BREAKING CHANGE:` → major, else patch).
- `CHANGELOG.md` (Keep a Changelog format): add entries under `## [Unreleased]` by hand, in the same PR as the change — that part is still manual. The release-time bookkeeping is automated: the `release` job renames `[Unreleased]` to the new version + today's date and commits that to `main` *before* creating the tag (so the tag lands on the commit that has the matching heading), then opens a `chore/changelog-sync-vX.Y.Z` PR against `dev` cherry-picking that exact commit — merge it to keep all three branches' `CHANGELOG.md` identical. That two-step (commit on `main`, then a separate PR into `dev`) is deliberate: a plain main-only commit would permanently diverge and conflict on every future `dev → stage → main` promotion (the same reason `release-please` was ruled out earlier) — routing the same change through an explicit PR avoids that. Bot-opened PRs don't trigger the `test` workflow (GitHub suppresses that for the default `GITHUB_TOKEN`, to prevent recursive triggering) — no checks showing up on that PR is expected, not broken.

## Merging a PR

Standing sequence for every PR into `dev` — do not merge on a partial signal, and do not merge two PRs concurrently.

1. **Wait for CI `test` to complete green.** Not "queued and looking fine" — completed. `gh pr checks <N> --watch --interval 20`. Note that `gh run watch` can exit non-zero while the run is still `in_progress`; re-check rather than trusting an early exit. `changes`/`deploy`/`release` showing `SKIPPED` on a PR is normal — those are push-triggered jobs.
2. **Wait for `aws-devops-agent/release-readiness-review` to finish and approve.** It is slower than `test` and frequently still `PENDING` after CI is green. The verdict string matters, not just the colour: `gh api repos/DataCrusade1999/supreme-enigma/commits/<sha>/status` → look for `Release readiness review: change approved`. It posts a **commit status, not a check-run**, so `gh api .../check-runs` will not show it.
3. **Read the inline comments — `gh pr view` does not show them, and there are two reviewers.** Findings from both bots are posted as inline review comments on specific lines, all at `gh api --paginate repos/DataCrusade1999/supreme-enigma/pulls/<N>/comments`. `--paginate` is not optional: the REST default is 30 per page, so without it a busy PR shows you a first page and hides the rest — a truncated read of this endpoint fails the same way as not reading it at all. `gh pr view <N> --json reviews,comments` returns only the review *summary* body (routinely empty) and issue-level comments, so it reports nothing while real findings sit on the PR — this is how #83's destination-strip bug was merged and then fixed in #84. Approval and findings are independent: the agent approved #83 *and* filed a correctness bug on it, so a green verdict is not a reason to skip this step. Each comment carries a root cause, a repro and a suggested diff; act on it or reply saying why not, before merging.
4. **Check both reviewers, not just the one with a status.** Two independent bots review every PR, and only the first has a commit status:
   - **`aws-devops-agent/release-readiness-review`** — verdict as a commit status (step 2), findings as inline comments.
   - **`chatgpt-codex-connector[bot]`** — inline comments only, tagged with P1/P2 severity badges. **No commit status, no check-run**, so nothing in `gh pr checks` or the status API reflects it. A green release-readiness verdict says nothing about whether this bot found something.

   On #99 the Codex bot filed all four findings (two P1s) while the devops agent filed none and approved. Filter the comments endpoint by `.user.login` to tell them apart, and triage every finding regardless of author.
5. **Merge only after all four.** `gh pr merge <N> --squash --delete-branch`, once `mergeable/mergeStateStatus` reads `MERGEABLE / CLEAN` (`UNSTABLE` just means checks are still running).
6. **Then pull.** `git checkout dev && git pull --ff-only origin dev`. Local `dev` drifts fast when several PRs land in a row; a stale local tree is how the wrong base gets used for the next branch.

Qualifiers that make the sequence actually safe:

- **A green `test` says nothing about `infra/`.** There is no Terraform validation anywhere in `deploy.yml` — no `validate`, no `fmt -check`, no `plan`. For any PR touching `infra/`, run `terraform plan` in a scratch worktree against real state *before* merging and confirm `No changes.`; CI cannot catch a provider bump that breaks the config. This is how the vercel v5 `sensitive`-now-required break was caught in #54.
- **Merge `lambda/`-touching PRs one at a time.** Two `deploy` jobs racing on the same function fail with `ResourceConflictException: An update is in progress for resource ...` — hit for real when #56 and #38 were merged back to back. Let each `deploy` finish before merging the next.
- **Take both reviews seriously — but verify their suggested fixes.** Neither bot is a rubber stamp. The devops agent independently found the #54 `sensitive` blocker (severity critical, with a repro), root-caused #44's Node floor, and caught #83's silent destination-strip bug with a working repro. The Codex bot found both P1s on #99. Read the comments before dismissing a red status as noise — and note the devops agent's two outputs sit in two different places (the verdict in a commit status, the findings in inline review comments), so checking one tells you nothing about the other.

  Their **problem reports** are well-researched and usually correct; their **suggested remedies** are not always, and two on #94/#95 would have caused real damage if applied as written. One proposed a catch-all `filter {}` S3 lifecycle rule alongside the prefix rules, claiming per-prefix rules take precedence — they do not, [AWS's conflict docs](https://docs.aws.amazon.com/AmazonS3/latest/userguide/lifecycle-conflicts.html) show an empty filter unions with them, so it would have expired `resume/current.pdf`. Another proposed moving the login rate-limit check to after `checkPassword`, which still compares the password on every request and so caps error responses rather than guesses. Confirm the problem yourself, then judge the fix separately — and check where the repro ran: the `X-Forwarded-For` spoofing finding was reproduced against `localhost:3000`, but Vercel overwrites that header and refuses to forward external values, so production was never exposed. Both bots accept reasoned disagreement in a thread reply; #94 and #95 stayed `change approved` after pushback.

## Project management

Work is tracked as GitHub issues, labeled `area: *` (bgm-looper/bgm-extractor/portfolio/infra/testing) and `priority: high/medium/low`, and triaged on the [BGM Looper Roadmap](https://github.com/users/DataCrusade1999/projects/4) project board (`Status`: Todo/In Progress/Done — GitHub's built-in workflows auto-update it on item-added/closed/PR-merged, already enabled by default, nothing to configure). Multi-phase initiatives (e.g. the portfolio UI overhaul) get an `epic`-labeled tracking issue with a task list linking each phase's issue. New issues should use the templates under `.github/ISSUE_TEMPLATE/` (feature/bug/chore — blank issues are disabled); PRs should reference the issue they close (`Closes #N`, per `.github/pull_request_template.md`). A design-spec-and-plan pair existing under `docs/superpowers/` does not imply an issue exists yet or vice versa — check the project board for current status, not just the docs.

## Writing

Remove all mannered prose — in docs, specs, plans, commit messages, PR descriptions, and blog content. Say the thing plainly; no throat-clearing, no rhetorical flourishes, no summary paragraphs restating what was just said.

## Gotchas

- **App env var is `APP_AWS_REGION`, not `AWS_REGION`** — deliberately named to avoid colliding with reserved AWS SDK/Vercel env vars.
- **`npm run build` hard-fails without `KEYSTATIC_GITHUB_CLIENT_ID`, `KEYSTATIC_GITHUB_CLIENT_SECRET`, and `KEYSTATIC_SECRET`** — Keystatic's `github` storage mode demands all three when Next collects page data for `/api/keystatic/[...params]`, so the build dies *after* a successful compile with `Failed to collect configuration for /api/keystatic/[...params]`. It looks like a build bug; it's a missing-env-var error. Any non-empty values get a local build through — real ones are only needed to actually authenticate against GitHub (i.e. to use the `/keystatic` admin UI). `npm test` and `npm run lint` are unaffected. These three are also the only Vercel env vars not managed by Terraform — see `.claude/rules/infra.md`.
- **Always pass both `--profile personal` and `--region us-east-1`, explicitly, on every manual `aws` CLI command in this project.**
  - Profile: it's a different AWS account (`223376380711`) than whatever the shell's default/`admin` profile points to (`688799538039`, unrelated account with no CE/Pricing/S3-list access) — this repo's actual infra (S3 buckets, ECR repo, Lambda) lives under `personal`. `.claude/settings.json` also sets `AWS_PROFILE=personal` for Claude Code sessions (that's what fixes the AWS MCP plugins, which pass no `--profile`) — but pass the flag anyway, since a plain shell doesn't inherit it.
  - Region: the `personal` profile's own configured default region is `ap-south-1` (Mumbai — presumably this user's general default elsewhere), but this project's real resources live in `us-east-1`. Terraform is never affected (its provider hardcodes `region = var.aws_region`, defaulting to `us-east-1`) — only raw `aws` CLI calls are at risk. Omitting `--region` silently queries `ap-south-1` and returns a misleading `ResourceNotFoundException`/`RepositoryNotFoundException` that looks like the resource is missing, when it's actually just the wrong region.
- S3 objects: uploads under `uploads/`, processed output under `outputs/` (same key, prefix swapped), all auto-expire after 1 day. Presigned URLs expire after 300s.
