# `web/` — Next.js frontend

Commands live in the root `CLAUDE.md`. This file is the per-file detail.

- `web/CLAUDE.md` is a one-line `@AGENTS.md` import and `web/AGENTS.md` is auto-generated — `next dev` re-creates both (they're committed deliberately, see 8e0efe0). Don't delete either; deleting just recreates an uncommitted diff. Don't hand-edit them either — put app guidance in this rules file instead.
- `web/TESTING.md` — unit-test conventions for async server components, and when to reach for e2e instead.
- The auth gate is `web/proxy.ts` (Next 16's rename of `middleware.ts` — there is no `middleware.ts`), tested by `web/proxy.test.ts`.
- Sign-in is through Cognito managed login (Google, email code, passkey) at `auth.ashutosh-pandey.com`: `/api/auth/login` stores state and a PKCE verifier in the signed `looper_oauth` cookie and redirects to Cognito; `/api/auth/callback` exchanges the code, verifies the ID token with `aws-jwt-verify`, and sets the session cookies. Both routes share `app/api/auth/redirect-to-cognito.ts`. The owner account was created by an admin, so Cognito never offers it passkey setup: the hub's "Add a passkey" link goes to `/api/auth/login?next=/api/auth/passkey`, which redirects to Cognito's `/passkeys/add`. The sign-in comes first because that page needs a live Cognito session, and without one it returns `?result=invalid_session`. `/passkeys/add` returns to the same callback with `?result=…` and no `code` or `state`, so the callback handles that shape before its state check and redirects to `/tools?passkey=added|failed`. The session is two AES-256-GCM cookies, `site_id` (the ID token) and `site_refresh` (the refresh token), keyed from `COOKIE_SECRET` in `web/lib/auth.ts`. Any Cognito user gets a session; `proxy.ts` refreshes the ID token when it has a minute left and asks the `Authorizer` (`web/lib/authz/`) for a decision on the `(tool, action)` that `actionFor()` maps the request to. An unmapped gated route is denied, and `lib/route-coverage.test.ts` fails for any gated `route.ts` or `page.tsx` without a row. Under Playwright, `AUTHZ_MODE=local` evaluates the same Cedar files in-process, and `web/e2e/session.ts` forges a cookie per role (`owner` by default, `friends`, `pending`). `AUTHZ_MODE=local` with `VERCEL` set denies everything.
- Only `/tools`, `/api/looper/*`, `/api/resume/*`, `/api/newsletter/*`, `/api/news-desk/*`, `/keystatic`, and `/api/keystatic/*` require a session — `web/lib/route-gate.ts`'s `isGatedPath()` is the single source of truth for what's gated; the public portfolio pages have no auth check at all. `/tools` is gated as a whole namespace rather than one prefix per tool: the hub page itself has to be behind the gate, and everything under it is a tool by definition, so a page added there is gated before anyone remembers to list it. The `/api/` prefixes stay explicit, since `/api/` also holds ungated routes. `ALWAYS_ALLOWED_PATHS` (`/login`) is carved back out of those gated prefixes, otherwise logging in would require being logged in. The login page lives at `/login` (moved from `/tools/bgm-looper/login` — it gates every tool, not just the looper) and sits outside the `(site)` route group deliberately, so it gets the root layout with no SiteHeader nav back into pages the visitor hasn't unlocked.
- **`route-gate.ts` also owns `TOOLS`, the one list of gated tools**, and three surfaces read it: the `/tools` hub renders a row per entry, `toolNameFor()` (the prefix → display-name lookup behind the login page's "Continuing to → X" strip) is derived from it, and `lib/site/commands.ts` carries one `open <tool>` command bar row per entry. Adding a tool is one entry in `TOOLS` plus one command row — the command labels are spelled out by hand rather than generated, because what a person types isn't derivable from a route (`/keystatic` → `open content-editor`). `TOOLS` key order is load-bearing for `toolNameFor()`'s prefix `find()`. The hub is deliberately *not* in `TOOLS`, so `toolNameFor("/tools")` is `null` and the gate shows its no-destination copy instead of "Continuing to Tools".
- Gated pages are reachable without typing a URL: a sign-in with no `next` lands on `/tools`, the hub links to each tool, and ⌘K carries `cd tools` / `open bgm-looper` / `open resume-admin` / `open content-editor`. Before this the resume admin and the Keystatic editor had no link anywhere and the login fallback dropped you on the looper. The looper's API routes were renamed from `/api/upload-url`/`/api/process` to `/api/looper/upload-url`/`/api/looper/process` to share one gated prefix with the page.
- **Styling is Tailwind CSS v4**, configured CSS-first in `web/app/globals.css` (no `tailwind.config.js`) — theme tokens (`--color-bg`, `--color-fg`, `--color-accent`, etc.) are declared once in a light `@theme` block and overridden in `:root.dark`, deliberately in both places so neither mode silently falls back to the other's value. Dark is the default; the toggle persists to `localStorage` and is applied pre-hydration by an inline script to avoid a flash.
- **`vitest.config.ts` sets `passWithNoTests: true`** deliberately, and setup imports `@testing-library/jest-dom/vitest` (not the plain `jest-dom` entrypoint) — both are load-bearing, don't "clean up". Its `exclude` spreads `configDefaults.exclude` before adding `**/.next/**` and `e2e/**` — Vitest replaces the default list entirely when one is given, so a hand-written list silently drops whichever defaults it forgets, and dropping `e2e/**` makes Vitest try to run the Playwright specs.
- `playwright.config.ts` builds and serves the app itself on port 3100 (180s timeout) and injects `COOKIE_SECRET`, dummy `COGNITO_*`, `AUTHZ_MODE=local` and all three `KEYSTATIC_*` — don't set them by hand, and don't point it at a dev server you started separately.
- **App env var is `APP_AWS_REGION`, not `AWS_REGION`** — deliberately named to avoid colliding with reserved AWS SDK/Vercel env vars.
- **`npm run build` hard-fails without `KEYSTATIC_GITHUB_CLIENT_ID`, `KEYSTATIC_GITHUB_CLIENT_SECRET`, and `KEYSTATIC_SECRET`** — Keystatic's `github` storage mode demands all three when Next collects page data for `/api/keystatic/[...params]`, so the build dies *after* a successful compile with `Failed to collect configuration for /api/keystatic/[...params]`. It looks like a build bug; it's a missing-env-var error. Any non-empty values get a local build through — real ones are only needed to actually authenticate against GitHub (i.e. to use the `/keystatic` admin UI). `npm test` and `npm run lint` are unaffected. These three are also the only Vercel env vars not managed by Terraform — see `.claude/rules/infra.md`.
- **`next build` type-checks test files.** A signature change that only breaks a `*.test.ts` (e.g. making `proxy()` async while `proxy.test.ts` used its return value directly) fails the Vercel build with `Failed to type check`, even though Vitest never runs there. Run `npx tsc --noEmit` in `web/` before pushing.
- **Reaching a preview by hand.** The `bgm-looper-git-<branch>-…` alias doesn't resolve when it exceeds DNS's 63-character label limit; take the deployment's real URL from `gh api repos/DataCrusade1999/supreme-enigma/deployments?sha=<sha>` → its status's `environment_url`. Scripted requests (`fetch`, `curl`) to a preview get Vercel's Security Checkpoint (`429`); open it in a browser (the Playwright MCP) instead.
