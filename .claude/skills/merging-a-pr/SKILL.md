# Merging a PR

Standing sequence for every PR into `dev` — do not merge on a partial signal, and do not merge two PRs concurrently.

1. **Wait for every CI job to complete green: `test`, plus `e2e-cross-os` on a PR into `main`.** Not "queued and looking fine" — completed. `gh pr checks <N> --watch --interval 20` — which prints each job's display `name:`, not its id, so look for `Tests`, and on a PR into `main` also `E2E (windows-latest)`, `E2E (macos-latest)` and `Summary`. Note that `gh run watch` can exit non-zero while the run is still `in_progress`; re-check rather than trusting an early exit. `changes`/`deploy`/`release` showing `SKIPPED` on a PR is normal — those are push-triggered jobs. `summary` runs only on PRs into `main`, writes the run's status table and gates nothing, so its result is informational. `promotion-guard` is its own workflow and runs only on promotions. **A PR that touches `infra/` must also have a green `Terraform` / `plan` job** (its own workflow, `.github/workflows/terraform.yml`). **A PR that touches only `docs/**`, `.claude/**` or `*.md` files gets no `CI/CD` run at all** — `deploy.yml`'s `pull_request` trigger has `paths-ignore` for them (#320). For such a PR, confirm the diff really is docs-only (`gh pr diff <N> --name-only`) and go on to step 2; any other file in the diff and a missing run is a problem. **CodeQL's `Analyze (…)` jobs and `CodeQL` check run on every PR, docs-only included** — they come from repository settings, not `deploy.yml`, so wait for them too, and treat a new alert they raise as a finding to triage in step 3.
2. **Request a devops agent review only where one is due — reviews are billed, so don't request them by default (#392).** The repo is public, so the agent starts no reviews on its own (#361); every review is one you request, and each costs money. Request one in exactly these cases:

   | PR | Review? |
   |---|---|
   | **`dev → stage` promotion** | **Always.** One review covers every commit in the batch; it is the main review. |
   | **`stage → main` promotion** | **Only if `stage` holds something the `dev → stage` review did not cover.** Find the head SHA that review ran on (the PR comment from that review records it) and run `git log --no-merges <reviewed-sha>..origin/stage`. Empty, or only `chore(changelog)` commits from a sync PR: skip the review and say so in a PR comment. Anything else: review the promotion. |
   | **PR into `dev` with a significant infra change** | **Yes.** Significant means the `Terraform` plan creates, destroys or replaces a resource, or the diff changes IAM (roles, policies, trust, OIDC), a Cedar policy under `infra/shared/cedar/`, or a security control (CloudTrail, GuardDuty, budgets, alarms). A provider lock bump or a tag/description edit whose plan is `No changes` or in-place-only is not significant. When unsure, review. |
   | **Any other PR into `dev`** (web, lambda, docs, changelog-sync, Dependabot batches without a significant infra change) | **No.** The gate is CI, the Codex bot (step 4) and your own review of the diff. |

   To request one: `create_release_readiness_review` with `githubPrContent: [{repository, prNumber, headBranch}]` and `skip_automated_testing: true`, poll `get_task` on a ~30s cadence until `COMPLETED`, then read `get_release_readiness_report`. Before requesting, check `list_tasks` (`task_type: RELEASE_READINESS_REVIEW`) for a review already run on the same head SHA, and never request a second one for a SHA that has one. If you push fixes after a review, do not re-review the whole PR — re-review only when the fix itself is a significant infra change. On a `dev → stage` promotion, those fix commits are then caught by the `stage → main` skip check and reviewed there, as a delta.

   This path posts no commit status and no inline comments: the gate is the report's `recommendedAction`, and its `risks` are the findings to triage in step 3. **`Standard Deployment` is the approval. `Deploy with Caution`, `BLOCK`, `Request Permissions` and `Insufficient Data` are not.** Any of those is a hard stop that outranks everything else, including your own severity triage in step 3: do not merge, do not "fix the findings and proceed", report the risks and wait for a human decision. Record the outcome on the PR in a comment — execution ID, the head SHA reviewed, recommended action, and what you did with each risk — since nothing else on GitHub shows it, and the `stage → main` skip check reads that SHA.

   If the repo is made private again, automated reviews come back as an `aws-devops-agent/release-readiness-review` **commit status** (not a check-run). Then the verdict must read `Release readiness review: change approved` with `state: success`; anything else is the same hard stop.
3. **Read the inline comments — `gh pr view` does not show them.** The Codex bot's findings (and the devops agent's, on a private repo) are posted as inline review comments on specific lines, all at `gh api --paginate repos/DataCrusade1999/supreme-enigma/pulls/<N>/comments`. `--paginate` is not optional: the REST default is 30 per page, so without it a busy PR shows you a first page and hides the rest — a truncated read of this endpoint fails the same way as not reading it at all. `gh pr view <N> --json reviews,comments` returns only the review *summary* body (routinely empty) and issue-level comments, so it reports nothing while real findings sit on the PR — this is how #83's destination-strip bug was merged and then fixed in #84. Approval and findings are independent: the agent approved #83 *and* filed a correctness bug on it, so a green verdict is not a reason to skip this step. Each comment carries a root cause, a repro and a suggested diff.

   **Triage every finding by severity, and act on that severity before merging.** Judge severity yourself, after confirming the problem in the source — do not inherit the bot's own label. Their labelling is inconsistent (the devops agent tags some findings `Severity: low` and leaves others unlabelled; the Codex bot uses P1/P2 badges) and it is assigned without knowing this project's threat model or what is already mitigated elsewhere.

   | Severity | Shape | Action |
   |---|---|---|
   | **High** | Reachable without authentication, data loss or corruption, breaks documented user-facing behaviour, or fails outright in production | **Fix on this PR** before merging |
   | **Medium** | Correctness bug reachable in normal use, security or cost hardening behind an auth gate, or a silent failure that misleads an operator | **Fix on this PR** before merging |
   | **Low** | Cosmetic, recovery-path-only, an observability nit, or a suggestion whose absence has no runtime effect | **File a GitHub issue**, quote the number in a reply on the thread, then resolve it |

   Two things that change how "fix on this PR" works:

   - **On a promotion PR (`dev → stage`, `stage → main`) you cannot commit to the PR.** Pushing to `stage` or `main` diverges it from `dev`. Fix on `dev` through its own PR instead; the promotion picks the commit up automatically and re-runs. That is what #108 did for the `%PDF-` finding on #106.
   - **Confirm the problem and judge the remedy separately.** Severity is about the problem, which these bots usually get right. The suggested diff is a different question and has been wrong three times — see the qualifiers below.
4. **Check the Codex bot on every PR, and the devops report wherever step 2 ran one.**
   - **`chatgpt-codex-connector[bot]`** — inline comments only, tagged with P1/P2 severity badges. **No commit status, no check-run**, so nothing in `gh pr checks` or the status API reflects it. On most PRs into `dev` it is now the only bot reviewing, so its silence carries more weight: confirm it actually reviewed.
   - **AWS DevOps Agent** — only on the PRs step 2 lists; its findings are the report's `risks`, not inline comments. A `Standard Deployment` says nothing about whether the Codex bot found something.

   On #99 the Codex bot filed all four findings (two P1s) while the devops agent filed none and approved. Triage every finding regardless of author.

   When the Codex quota is spent, the bot posts an issue-level comment, "You have reached your Codex usage limits for code reviews", instead of reviewing. That PR had no Codex review: say so when reporting, rather than counting its silence as a pass.
5. **Resolve every thread you actually addressed.** Resolving is GraphQL-only — REST cannot do it, and `gh pr resolve` does not exist. List the threads, then resolve by id:

   ```bash
   gh api graphql -f query='{ repository(owner:"DataCrusade1999",name:"supreme-enigma"){
     pullRequest(number:<N>){ reviewThreads(first:20){ nodes{ id isResolved path line
       comments(first:1){ nodes{ body } } } } } } }'

   gh api graphql -f query='mutation($id:ID!){ resolveReviewThread(input:{threadId:$id}){
     thread{ isResolved path } } }' -f id=<PRRT_...>
   ```

   Reply saying what you did *before* resolving — a resolved thread with no reply loses the reason, and the next person cannot tell a fix from a dismissal. Three dispositions count as handled: **fixed**, **answered with evidence**, or **filed as an issue** and the number quoted in the reply. Filing is what makes a deferral safe to resolve — the finding survives somewhere durable instead of dying with the PR. Never resolve one you are simply dropping, or one still awaiting a verification you have not run: leave those open and say why in the thread. Findings posted as issue-level comments (the agent's "Additional findings on related files" block) are not review threads and have no resolve action; answer them with a reply.

6. **Merge only after all four**, once `mergeable/mergeStateStatus` reads `MERGEABLE / CLEAN` (`UNSTABLE` just means checks are still running). **The merge method depends on which kind of PR it is, and getting it wrong on a promotion is destructive:**
   - **Feature/fix branch → `dev`:** `gh pr merge <N> --squash --delete-branch`. The branch is disposable and one squashed commit per PR is what `release`'s Conventional-Commit version bump reads.
   - **`chore/changelog-sync-*` → `dev`:** `gh pr merge <N> --merge --delete-branch`. **Never `--squash`** — the branch merges `main` into `dev` on purpose, and squashing throws that ancestry away, which is exactly the #168 bug. Deleting the branch is fine here; it is disposable.
   - **Promotion `dev → stage` or `stage → main`:** `gh pr merge <N> --merge`, and **never `--delete-branch`** — that flag would delete `dev` or `stage`, which are permanent branches. Squashing is equally wrong: it collapses the promoted commits into one new commit that exists on neither side's history, so the branches permanently diverge and every later promotion conflicts. This is the same reason `release-please` was ruled out. Past promotions landed as real merge commits with two parents (`b115ebe` for #63, `6506a1a` for #106) — `git log origin/stage --format='%h %p %s'` shows the two-parent shape to check against. Into `stage`, the `stage-promotion-prs` ruleset enforces this: only `--merge` is allowed, every review thread must be resolved, and `Tests` and `promotion-guard` must be green, so `mergeStateStatus` reads `BLOCKED` until they are. The one legitimate `--admin` is a docs-only promotion, which gets no `Tests` run: confirm the diff with `gh pr diff <N> --name-only` and that `promotion-guard` passed, then `gh pr merge <N> --merge --admin`. Never use `--admin` to get past a failing check or an open thread. Into `main` nothing is enforced; the same rules apply by convention.
7. **Then pull.** `git checkout dev && git pull --ff-only origin dev`. Local `dev` drifts fast when several PRs land in a row; a stale local tree is how the wrong base gets used for the next branch.

Qualifiers that make the sequence actually safe:

- **A green `test` says nothing about `infra/`; the `Terraform` workflow does.** For any PR touching `infra/`, read the plan comment it posted on the PR: each stack must say `No changes` or exactly the intended diff, with no `⚠ destroys or replaces` line you did not intend. A local `terraform plan` is the fallback when the workflow cannot run. A provider bump that breaks the config fails that job, which is how the vercel v5 `sensitive`-now-required break would surface today (it was caught by a local plan in #54).
- **A PR that changes the plan role's own permissions can't get a green `plan` job.** The plan runs as `bgm-looper-tf-plan` before the PR's grant exists, so it fails on the permission the PR adds (#360). Check the failed log names only that permission, then run the local plan (`AWS_PROFILE=personal terraform plan -var-file=terraform.tfvars -lock=false` in the stack directory) and paste its summary into the PR. That local plan is the gate.
- **Re-run a failure that the same commit doesn't reproduce elsewhere.** On #356 the Linux `test` job failed building with `Can't resolve '@vercel/turbopack-next/internal/font/google/font'`, which is how a failed Google Fonts download shows up, while the same commit passed on Windows, macOS and stage's Linux push run. `gh run rerun <id> --failed` passed. Read the error first: a real failure reproduces.
- **Merge `lambda/`-touching PRs one at a time.** Two `deploy` jobs racing on the same function fail with `ResourceConflictException: An update is in progress for resource ...` — hit for real when #56 and #38 were merged back to back. Let each `deploy` finish before merging the next.
- **Take both reviews seriously — but verify their suggested fixes.** Neither bot is a rubber stamp. The devops agent independently found the #54 `sensitive` blocker (severity critical, with a repro), root-caused #44's Node floor, and caught #83's silent destination-strip bug with a working repro. The Codex bot found both P1s on #99. Read the findings before dismissing a blocking verdict as noise.

  Their **problem reports** are well-researched and usually correct; their **suggested remedies** are not always, and two on #94/#95 would have caused real damage if applied as written. One proposed a catch-all `filter {}` S3 lifecycle rule alongside the prefix rules, claiming per-prefix rules take precedence — they do not, [AWS's conflict docs](https://docs.aws.amazon.com/AmazonS3/latest/userguide/lifecycle-conflicts.html) show an empty filter unions with them, so it would have expired `resume/current.pdf`. Another proposed moving the login rate-limit check to after `checkPassword`, which still compares the password on every request and so caps error responses rather than guesses. Confirm the problem yourself, then judge the fix separately — and check where the repro ran: the `X-Forwarded-For` spoofing finding was reproduced against `localhost:3000`, but Vercel overwrites that header and refuses to forward external values, so production was never exposed. Both bots accept reasoned disagreement in a thread reply; #94 and #95 stayed `change approved` after pushback.

## Dependabot PRs

**Land open Dependabot PRs as one batch, not one at a time.** The goal is the fewest Actions runs. Each merge into `dev` is a push run that is never cancelled, and each merge that touches a shared lock file (`web/package-lock.json`, `lambda/requirements.txt`, `infra/*/.terraform.lock.hcl`) makes the remaining Dependabot PRs conflict. Dependabot then rebases every one of them, and each rebase is a full PR run. `groups:` in `.github/dependabot.yml` keeps this to about one PR per ecosystem (two for Terraform, one per directory), but majors are ungrouped and PRs still pile up between merges. Whenever more than one is open:

1. **Do not `@dependabot rebase` stale PRs to re-check them.** Every rebase is a full run. Their old results only need to be good enough to pick what goes in the batch; the batch PR's own run is the real gate.
2. **File one issue and cut one `chore/` branch from `dev`.** `git merge` each `origin/dependabot/...` branch into it. On a lock-file conflict, take either side and regenerate: `npm install --package-lock-only` in `web/`. For a Terraform lock, take each provider's block from its own branch rather than running `terraform init -upgrade`, which only hashes the current platform. Then check that `npm install --package-lock-only` leaves the lock unchanged.
3. **Run the whole gate locally before pushing**, so the PR goes green on its first run: `npm ci`, `npm test`, `npm run lint`, `npm run build` (dummy Keystatic vars), `node --test ".github/scripts/*.test.mjs"`, and lambda `pytest` after `pip install -r requirements.txt` into `.venv`. The four stateful Terraform stacks need no local plan: the batch PR is opened by the owner, so its `Terraform` run plans them (that workflow skips Dependabot's own PRs, which get no secrets or OIDC token). CI never plans `infra/bootstrap`, so when its lock file is in the batch run `terraform init && terraform validate` there.
4. **Open the PR and put the versions that actually merged in its body.** Rebased Dependabot branches often resolve newer versions than their titles say — #311's titles said aws 6.66.0 and vercel 5.16.0, and the locks held 6.67.0 and 5.18.0.
5. **Close every original Dependabot PR before merging the batch**, with "Superseded by #N". Closing starts no run. Merging first moves `dev`, every original conflicts, and Dependabot rebases them all — the run cascade this section exists to avoid. Dependabot will not re-offer those exact versions, which does not matter since the batch installs them; `gh pr reopen` works if the batch is abandoned.
6. **Merge with the normal steps 1–7 above**, `--squash` with a `chore(deps):` subject. The batch carries every `lambda/` bump in one `deploy`, which also satisfies the one-`lambda/`-PR-at-a-time rule.

A single open Dependabot PR needs none of this: merge it through the normal steps.

Dependabot security updates are on (#367), so a fixable advisory opens its own ungrouped PR outside the monthly schedule. Merge it through the normal steps rather than holding it for the next batch.

#311 landed eleven Dependabot PRs this way for two runs — one on the PR, one push run on `dev` — where merging them one by one would have taken eleven push runs plus the rebase runs between them.

## The changelog-sync PR

The release-time `CHANGELOG.md` bookkeeping is automated: the `release` job renames `[Unreleased]` to the new version + today's date and commits that to `main`, then opens a `chore/changelog-sync-vX.Y.Z` PR against `dev` that **merges `main` into a branch cut from `dev`**, and only then creates the tag and GitHub Release. Merge that PR and `dev`'s `CHANGELOG.md` becomes byte-identical to `main`'s. The tag is deliberately last: the sync step is fatal on failure, so tagging first would publish a release with no reconciliation behind it. Because it is last, re-running the job *is* the recovery path — every step in it is idempotent by version (not by version+date, which would insert a second heading on a re-run that happens the next day). `stage` is not identical until the next `dev → stage` promotion carries the heading across; that lag is normal, and the invariant that matters is that the release commit is an *ancestor* of all three, not that the file matches at every instant. It merges rather than cherry-picks because #168 showed a copy is not enough: a cherry-pick (or a squash-merge of the sync PR) leaves the release commit outside `dev`'s history, so the next promotion's merge base still predates the heading, git sees two insertions under the same `## [Unreleased]` anchor, and **silently** emits the heading twice with the new entries filed under the wrong copy. The sync PR must therefore be merged with `--merge` and merged *promptly* — until it lands, the next promotion has that same broken merge base. If entries land on `dev` between the promotion and the release job, they did not ship in that version. `.github/scripts/changelog-sync.py` builds the branch's `CHANGELOG.md` by copying `main`'s released section verbatim and re-adding only `dev`'s un-promoted entries under `## [Unreleased]`, so they stay filed correctly with nothing to move by hand; the PR body says how many. The two files cannot drift, because the released section is copied rather than re-derived. If the script finds entries under the version on `main` that were never on `dev`'s `[Unreleased]` — a direct commit to `main`, or an entry reworded on `dev` after the promotion — it says so in the PR *title*; that one does need a human look. The step is fatal on every other failure now (it used to warn and let `release` report success, which is how three releases drifted unnoticed). That two-step (commit on `main`, then a separate PR into `dev`) is deliberate: a plain main-only commit would permanently diverge and conflict on every future `dev → stage → main` promotion (the same reason `release-please` was ruled out earlier) — routing the same change through an explicit PR avoids that.

**The sync PR gets CI, but the run is gated until someone approves it.** Because `github-actions[bot]` opens the PR, GitHub creates the `pull_request` run and immediately finishes it as `completed/action_required` without executing a single job. Only Vercel reports, so `gh pr checks` looks plausibly green while the test jobs are simply absent — the dangerous shape, since missing checks read as "bot PRs don't get CI here" rather than as a problem. Approve the run with `gh api -X POST repos/DataCrusade1999/supreme-enigma/actions/runs/<run_id>/approve` and everything behaves normally. On #206 that took the test jobs from never-started to a 4m26s pass plus a `change approved` verdict. **Absent test jobs on a sync PR mean gated, not skipped — approve it and wait, never merge on the strength of a green Vercel check.** This is long-standing behaviour, not a recent change. The one exception came with #320: a sync PR whose diff is only `CHANGELOG.md` matches `deploy.yml`'s docs `paths-ignore` and gets no run at all, gated or otherwise. Tell the two apart with `gh run list --branch <sync branch> --workflow CI/CD`: a run in `action_required` needs approving; no run plus `gh pr diff <N> --name-only` showing only `CHANGELOG.md` is expected. Tracked in #207, which also asks whether the gate can be lifted for this repo's own bot.
